    What a backend is the big picture

    The backend is the part of an app users never see. It holds the data, enforces the rules, and answers every request the frontend makes.

    Client and server

    A server is a program that waits for requests and sends back responses. It runs on a computer somewhere else, usually in a data center. The client is whatever sends the request: a browser, a mobile app, another server, or a curl command in your terminal.

    One backend usually serves many kinds of client at once. The website, the Android app and a partner's integration can all call the same API.

    What the backend is responsible for

    • Data. Saving and reading it from a database.
    • Rules. "You can't withdraw more than your balance." The frontend can check this too, but only the server's check counts.
    • Identity. Who is logged in and what they may do.
    • Secrets. API keys, payment credentials, database passwords. These never go to the browser.
    • Work in the background. Sending emails, resizing images, generating reports.

    The life of one request

    Follow a user clicking "Add task" in a to-do app:

    1. The frontend sends POST /api/tasks with the task as JSON.
    2. DNS resolves the domain, and the request travels over HTTPS to a load balancer, which picks one server.
    3. Express receives it and runs it through middleware: log it, parse the JSON, check the login token, validate the body.
    4. The route handler calls a service, which applies the rules and saves the task through the database layer.
    5. The database writes the row and returns it.
    6. The handler sends 201 Created with the saved task as JSON.
    7. The frontend updates the screen.

    Every stage in this handbook zooms into one or more of these steps. Steps 1 and 7 happen in the browser. The Frontend handbook covers them in fetch and React state, and walks the same click through both sides in How frontend and backend meet.

    Stateless servers

    HTTP has no memory. Each request must carry everything the server needs, such as the login token. The server should not rely on remembering the previous request in a variable, because the next request may hit a different copy of the server.

    Anything that must persist goes into a database or a cache like Redis. This one habit is what later lets you run ten copies of your server behind a load balancer.

    Never trust the client

    Anyone can open DevTools, edit your JavaScript, or send requests with curl. So frontend validation is only for user convenience. The backend must check every input, every permission and every price again, as if the frontend did not exist.

    Backend languages

    Node.js (JavaScript/TypeScript), Python (Django, FastAPI), Java (Spring Boot), Go, C# (.NET), PHP (Laravel) and Ruby (Rails) all do the same job. We use Node because it is the same language as the frontend, which means one language and shared types across the whole stack.

    Go deeperOpen DevTools, then Network, on any app you use. Click something and read the request and response the click sends. Then look at roadmap.sh/backend to see where each stage of this handbook fits.

    HTTP in depth the language of the web

    Every backend speaks HTTP. A request is plain text with a method, a path, headers and an optional body. A response has a status code, headers and a body.

    What a request and a response look like

    POST /api/tasks HTTP/1.1          <- method, path, version
Host: api.example.com              <- headers
Content-Type: application/json
Authorization: Bearer eyJhbGci...

{"title": "Learn Express"}         <- body
    HTTP/1.1 201 Created               <- status
Content-Type: application/json     <- headers
Location: /api/tasks/42

{"id": 42, "title": "Learn Express", "done": false}

    Your browser, fetch, Postman and Express all build or read this same text. Frameworks just hide it behind objects like req and res.

    Methods, safe and idempotent

    MethodMeaningSafeIdempotent
    GETreadyesyes
    POSTcreate, or run an actionnono
    PUTreplace the whole thingnoyes
    PATCHchange some fieldsnonot always
    DELETEremovenoyes

    Safe means it changes nothing. Idempotent means sending it twice has the same effect as sending it once. This matters when a network retry sends a request again. Two identical POSTs can create two orders.

    PUT and PATCH, side by side

    Both update, but they mean different things. PUT sends the whole resource and replaces what is stored, so any field you leave out is gone. PATCH sends only the fields to change.

    // stored: {"name":"Eswar","email":"e@x.com","city":"Hyderabad"}

PUT /users/5
{"name":"Eswar","email":"new@x.com"}

// result: {"name":"Eswar","email":"new@x.com"}
// city was removed
    // stored: {"name":"Eswar","email":"e@x.com","city":"Hyderabad"}

PATCH /users/5
{"email":"new@x.com"}

// result: {"name":"Eswar","email":"new@x.com","city":"Hyderabad"}
// only email changed

    Most "edit profile" forms want PATCH. Use PUT when the client always has the full object, such as saving a whole settings document.

    Status codes by family

    FamilyCommon ones
    2xx success200 OK, 201 Created, 204 No Content
    3xx redirect301 moved permanently, 302 temporary, 304 not modified (use your cache)
    4xx client's fault400 bad input, 401 not logged in, 403 not allowed, 404 not found, 409 conflict, 422 invalid data, 429 too many requests
    5xx server's fault500 crashed, 502 bad gateway, 503 unavailable, 504 timeout

    The correct code lets the frontend react properly without reading the message. A 401 means "show the login page". A 500 means "try again later".

    Headers worth knowing

    • Content-Type: the format of the body, usually application/json.
    • Accept: what format the client wants back.
    • Authorization: credentials, often Bearer <token>.
    • Cookie / Set-Cookie: send and set cookies.
    • Cache-Control, ETag: caching rules.
    • Location: where a new resource lives, or where to redirect.
    • Origin: which site the request came from, used by CORS.

    Cookies

    A cookie is a small value the server asks the browser to store. The browser sends it back automatically with every request to that site. That makes cookies the classic way to keep someone logged in.

    Set-Cookie: sid=abc123; HttpOnly; Secure; SameSite=Lax; Max-Age=86400
    • HttpOnly: JavaScript cannot read it, so XSS cannot steal it.
    • Secure: only sent over HTTPS.
    • SameSite: limits sending it from other sites, which blocks most CSRF.
    • Max-Age / Expires: how long it lives.

    HTTPS and TLS

    HTTPS is HTTP inside an encrypted TLS connection. The encryption stops anyone on the network from reading or changing traffic, and the certificate proves the server really owns the domain. Free certificates come from Let's Encrypt, and most hosts set this up for you. Never send passwords or tokens over plain HTTP.

    Body formats

    APIs mostly use JSON. HTML forms send application/x-www-form-urlencoded. File uploads use multipart/form-data. The Content-Type header tells the server which parser to use, which is why a missing header often leaves you with an empty req.body.

    HTTP/1.1, 2 and 3

    The meaning (methods, codes, headers) is the same in all three. HTTP/2 sends many requests over one connection at once. HTTP/3 runs over QUIC to handle bad networks better. Your hosting or proxy usually handles this, and your Express code does not change.

    Go deeperRun curl -v https://example.com and read every line. Look up each header you don't recognize in MDN's HTTP headers reference.

    Node.js JavaScript on the server

    Node.js runs JavaScript outside the browser. It uses Chrome's V8 engine plus libraries to read files, open network ports and talk to the operating system.

    What Node is, and is not

    Node is a runtime, not a framework and not a language. The browser gives JavaScript document and window. Node gives it fs, http, process and the rest of the server toolkit instead. There is no DOM in Node.

    Node is good at handling many connections that each wait on input and output: APIs, chat, streaming. It is weaker at long CPU-heavy work like video encoding.

    The event loop and non-blocking I/O

    Node runs your JavaScript on one thread. When code asks for a file or a database query, Node hands the wait to the operating system or a small background thread pool (libuv) and moves on. When the result is ready, its callback joins a queue. This is how one thread serves thousands of users.

    This is the same event loop the browser uses, which the Frontend handbook explains with a waiter analogy. The order is: all synchronous code first, then promise callbacks (microtasks), then timers and I/O callbacks. Predict the output, then run it:

    console.log("1 start");
setTimeout(() => console.log("2 timeout"), 0);
Promise.resolve().then(() => console.log("3 promise"));
console.log("4 end");
    Output appears here.

    Sync lines run first (1, 4). The promise callback is a microtask, so it runs as soon as the sync code ends (3). The timer waits for the next turn of the loop, even at 0 ms (2).

    Don't block the loop

    Because there is one thread, a slow synchronous task freezes every user, not just one. Common mistakes:

    • fs.readFileSync inside a request handler. Use await fs.promises.readFile.
    • A huge loop or heavy JSON parsing per request.
    • Password hashing with a sync function. Use the async version.

    For real CPU work, use worker threads or move it to a background job.

    Modules: ESM and CommonJS

    Built-in modules

    node:fs for files, node:path for joining paths safely, node:http for raw servers, node:crypto for hashes and random IDs, node:events for event emitters, node:stream for processing big data piece by piece. Modern Node also has fetch and a test runner built in.

    process and environment variables

    const port = process.env.PORT || 3000;
const dbUrl = process.env.DATABASE_URL;

    process.env holds configuration from outside the code. Locally it comes from a .env file (node --env-file=.env or the dotenv package). In production the host sets it. Never commit real .env files.

    npm scripts and watch mode

    "scripts": {

  "start": "node src/server.js",

    --watch restarts the server when you save, which used to need nodemon. Run with npm run dev.

    A server with no framework

    import http from "node:http";
http.createServer((req, res) => {
  res.writeHead(200, { "Content-Type": "application/json" });
  res.end(JSON.stringify({ hello: "world" }));
}).listen(3000);

    This works, but you would have to parse URLs, bodies and routes by hand. Express does that for you.

    Express basics routes and handlers

    Express is a small framework on top of Node's http module. It maps a method and URL to a function, and gives you friendly req and res objects.

    A first server

    import express from "express";
const app = express();
app.use(express.json());          // parse JSON bodies

app.get("/api/health", (req, res) => {
  res.json({ ok: true });
});

app.listen(3000, () => console.log("on :3000"));

    Install with npm install express. Visit http://localhost:3000/api/health to see it work.

    Routing

    A route is a method plus a path plus a handler. Express checks routes top to bottom and runs the first match.

    app.get("/api/users", listUsers);
app.get("/api/users/:id", getUser);      // :id is a param
app.post("/api/users", createUser);
app.patch("/api/users/:id", updateUser);
app.delete("/api/users/:id", deleteUser);

    Reading the request

    WhereExample URL or bodyIn Express
    Path param/users/5req.params.id is "5"
    Query string/users?page=2req.query.page is "2"
    Body{"name":"Eswar"}req.body.name
    HeaderAuthorization: ...req.get("authorization")

    Params and query values are always strings. Convert with Number() and validate them.

    Sending the response

    res.json(user);                      // 200 + JSON
res.status(201).json(newUser);       // created
res.status(404).json({ error: "User not found" });
res.sendStatus(204);                 // no body
res.redirect("/login");

    Send exactly one response per request. Forgetting to respond leaves the client hanging. Responding twice throws "headers already sent".

    Splitting routes with Router

    // routes/users.js
const router = express.Router();
router.get("/", listUsers);
router.get("/:id", getUser);
export default router;

// app.js
app.use("/api/users", usersRouter);

    Each feature gets its own file, and app.js stays short.

    Static files

    app.use(express.static("public")) serves files from a folder as-is: images, a built React app, a robots.txt. In bigger setups a CDN does this instead.

    Express 4 and 5

    Express 5 is current. The main change you will feel: if an async handler throws or its promise rejects, Express 5 passes the error to your error middleware automatically. In Express 4 you needed try/catch or a wrapper in every async handler, which you will see in older tutorials.

    Go deeperRead the Routing guide on expressjs.com. Then build an in-memory notes API (an array, no database) with all five CRUD routes.

    Middleware the request pipeline

    Middleware is the most important idea in Express. A request passes through a chain of small functions before it reaches your handler. Each one can read it, change it, stop it, or pass it on.

    How it works

    A middleware function receives (req, res, next). It either sends a response and ends the chain, or calls next() to hand over to the next function. Express runs them in the order you app.use() them, so order matters. A parser that runs after your route is useless.

    function logger(req, res, next) {
  console.log(req.method, req.url);
  next();                       // pass it on
}
app.use(logger);

    A guard: auth middleware

    function requireAuth(req, res, next) {
  const token = req.get("authorization")?.split(" ")[1];
  if (!token) return res.status(401).json({ error: "Not logged in" });
  req.user = verifyToken(token);   // attach for later handlers
  next();
}
app.get("/api/me", requireAuth, (req, res) => res.json(req.user));

    Middleware can also add data to req for later handlers, like req.user here.

    Middleware you will use everywhere

    • express.json(): parses JSON bodies into req.body.
    • cors(): lets your frontend's origin call the API.
    • helmet(): sets security headers.
    • morgan or pino-http: request logging.
    • express-rate-limit: blocks clients that send too many requests.
    • cookie-parser: reads cookies into req.cookies.
    • compression: gzips responses.

    Error handling

    An error middleware has four arguments. Put it last. Any error thrown in a handler, or passed with next(err), lands here, so you format errors in one place and never leak stack traces to users.

    app.use((req, res) => res.status(404).json({ error: "Not found" }));

app.use((err, req, res, next) => {
  console.error(err);
  res.status(err.status || 500).json({
    error: err.expose ? err.message : "Something went wrong",
  });
});

    See the pipeline

    Pick a request and watch where it stops. This is a simulation, but the order and status codes match a typical Express app.

    Press "Send request".

    Go deeperRead Using middleware on expressjs.com. Then write your own logger that prints how long each request took, using res.on("finish").

    REST API design a contract with the frontend

    An API is a promise to everyone who calls it. Good design makes it predictable: once you know one endpoint, you can guess the rest.

    Resources and CRUD

    REST treats data as resources at URLs. URLs are nouns, plural. The HTTP method is the verb. Most apps are mostly Create, Read, Update, Delete.

    ActionRequestSuccessCommon failures
    ListGET /users200 + array401
    Read oneGET /users/5200 + object404
    CreatePOST /users201 + new object400, 409 email taken
    UpdatePATCH /users/5200 + updated object400, 403, 404
    DeleteDELETE /users/5204403, 404

    Related data nests one level: GET /users/5/posts. Avoid verbs in URLs like /getUsers or /deleteUser/5.

    Filtering, sorting and pagination

    GET /products?category=books&sort=-price&page=2&limit=20

    Never return an unbounded list. Ten rows in development become a million in production. Offset pagination (page, limit) is simple. Cursor pagination (?after=lastId) stays fast on huge tables and is what infinite-scroll feeds use. The response tells the client where to continue:

    GET /posts?limit=20&after=post_981
{
  "data": [ /* 20 posts */ ],
  "nextCursor": "post_961"      // null when there are no more
}

    Validating input

    Check every body, param and query before using it. A schema library describes the shape once and gives clear errors.

    import { z } from "zod";
const NewUser = z.object({
  name: z.string().min(1),
  email: z.string().email(),
  age: z.number().int().min(13).optional(),
});
const result = NewUser.safeParse(req.body);
if (!result.success) return res.status(400).json(result.error.issues);

    A consistent error shape

    {
  "error": {
    "code": "EMAIL_TAKEN",
    "message": "That email is already registered",
    "field": "email"
  }
}

    Pick one shape and use it for every error. The frontend can then show messages next to the right field without special cases.

    Versioning

    Once a mobile app ships, you cannot force everyone to update. Breaking changes go into a new version, /api/v2/..., while v1 keeps working. Adding a new optional field is not breaking. Renaming or removing one is.

    Idempotency keys

    For payments and orders, the client sends a unique Idempotency-Key header. If the same key arrives twice, because the user double-clicked or the network retried, the server returns the first result instead of charging twice. Stripe's API works this way.

    Documenting and testing APIs

    OpenAPI (Swagger) describes every endpoint in one file and can generate an interactive docs page. For trying requests by hand, use Postman, Insomnia, Thunder Client in VS Code, or curl:

    curl -X POST localhost:3000/api/users \
  -H "Content-Type: application/json" \
  -d '{"name":"Eswar","email":"e@x.com"}'

    GraphQL and RPC, briefly

    GraphQL uses one endpoint where the client asks for exactly the fields it needs. That helps when many different screens need different slices of data. tRPC and gRPC call server functions more directly. REST is still the default for public APIs and the one to learn first.

    Go deeperBrowse two well-designed APIs, the Stripe API reference and GitHub's REST docs, and notice their URL, status code, pagination and error patterns.

    Databases where data lives

    Variables vanish when the server restarts. A database stores data on disk, keeps it consistent, and finds what you ask for quickly. This stage connects to the DBMS/ folder in this repo.

    SQL and NoSQL

    SQL (relational)NoSQL
    ExamplesPostgreSQL, MySQL, SQLiteMongoDB (documents), Redis (key-value), Cassandra, DynamoDB
    ShapeTables with a fixed schema, rows and columnsFlexible documents, key-value pairs, wide columns
    RelationsForeign keys and JOINs, built inUsually embed data, or join in your own code
    ConsistencyStrong, with ACID transactionsVaries, often trades some consistency for scale
    Good forMost apps: users, orders, payments, anything relatedCaches, sessions, logs, very large or loosely structured data

    If you are unsure, pick PostgreSQL. It handles relational data well, and it can also store JSON columns when you need flexibility.

    Keys and relationships

    A primary key identifies a row uniquely, usually id. A foreign key is a column pointing at another table's primary key, such as orders.user_id pointing to users.id.

    • One-to-one: user and profile.
    • One-to-many: a user has many orders. The foreign key goes on the "many" side.
    • Many-to-many: students and courses. Needs a join table, enrollments(student_id, course_id).

    SQL essentials

    SELECT u.name, COUNT(o.id) AS orders
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE u.created_at > '2026-01-01'
GROUP BY u.name
HAVING COUNT(o.id) > 3
ORDER BY orders DESC
LIMIT 10;

    Also know INSERT, UPDATE, DELETE, the different JOINs, subqueries and window functions. Practice them in DBMS/SQL Practice.

    Normalization

    Store each fact in one place. If a customer's address is copied into every order row, changing it means updating hundreds of rows, and some will be missed. Normalization splits data into tables linked by keys. Sometimes you denormalize on purpose, copying data to make reads faster, but do it knowingly.

    Indexes

    An index is like the index at the back of a book. Without one, the database reads every row to find email = 'x'. With one, it jumps straight there, usually through a B-tree. The cost is slower writes and more disk, so index the columns you filter, join and sort by, not everything.

    CREATE INDEX idx_orders_user ON orders(user_id);

    Use EXPLAIN on a slow query to see whether it uses an index.

    Transactions and ACID

    Moving money is two writes: subtract from A, add to B. If the server crashes between them, money disappears. A transaction makes the group all-or-nothing.

    BEGIN;
UPDATE accounts SET balance = balance - 500 WHERE id = 1;
UPDATE accounts SET balance = balance + 500 WHERE id = 2;
COMMIT;   -- or ROLLBACK on error

    ACID: Atomic (all or nothing), Consistent (rules hold), Isolated (concurrent transactions don't see each other's half-work), Durable (committed data survives a crash).

    The same transfer from Node with Prisma:

    await prisma.$transaction([
  prisma.account.update({ where: { id: 1 }, data: { balance: { decrement: 500 } } }),
  prisma.account.update({ where: { id: 2 }, data: { balance: { increment: 500 } } }),
]);   // both happen, or neither does

    Connection pools

    Opening a database connection is slow, and databases allow only a limited number. A pool keeps a few connections open and lends them out per query. Drivers and ORMs do this for you. In serverless setups you often need an external pooler such as PgBouncer or your host's pooling URL.

    Connection strings

    Your app finds the database through one URL, kept in the DATABASE_URL environment variable and never in code.

    postgresql://app_user:s3cret@db.example.com:5432/notes?sslmode=require

scheme      postgresql://
user        app_user
password    s3cret
host:port   db.example.com:5432
database    notes
options     sslmode=require   (encrypt the connection)

    MySQL starts with mysql:// and MongoDB with mongodb+srv://. If the password contains characters like @ or /, URL-encode them or the string breaks.

    Hosted databases

    You rarely run a production database yourself. Neon and Supabase (Postgres), PlanetScale (MySQL and Postgres) and MongoDB Atlas handle backups, upgrades and scaling, and give you the connection string to paste into .env. Locally, Docker or SQLite is enough.

    Go deeperDo the official PostgreSQL tutorial. Then design the tables for a small library system (books, members, loans) and write the five queries you would need most.

    Using a database from Node drivers, ORMs, migrations

    Your Express code needs a way to send queries and get rows back as JavaScript objects. There are three levels, from raw SQL to a full ORM.

    Driver, query builder, ORM

    • Driver (pg, mysql2): you write SQL strings. Full control, most typing.
    • Query builder (Knex, Kysely, Drizzle): build SQL with functions. Close to SQL, with types.
    • ORM / ODM (Prisma, Sequelize, TypeORM; Mongoose for MongoDB): work with models and objects. Fastest to start, hides the SQL.

    Learn enough raw SQL to read what your ORM generates. When something is slow, that's where you look.

    Prisma, a typical ORM

    // schema.prisma
model User {
  id    Int    @id @default(autoincrement())
  email String @unique
  posts Post[]
}
model Post {
  id       Int    @id @default(autoincrement())
  title    String
  author   User   @relation(fields: [authorId], references: [id])
  authorId Int
}
    const users = await prisma.user.findMany({
  where: { email: { endsWith: "@gmail.com" } },
  include: { posts: true },
});

    Mongoose for MongoDB

    const User = mongoose.model("User", new mongoose.Schema({
  name: String,
  email: { type: String, required: true, unique: true },
}));
const u = await User.findOne({ email: "e@x.com" });

    MongoDB itself has no schema. Mongoose adds one in your code so documents stay consistent.

    Migrations

    A migration is a versioned file that changes the schema: "add column phone to users". They are committed to Git and run in order on every machine and on production, so all databases end up identical. Never change a production schema by hand. Seed scripts fill a fresh database with test data.

    npx prisma migrate dev --name add_phone

    The N+1 query problem

    You load 50 posts (1 query), then loop and load each author (50 more queries). That is 51 round trips where 1 or 2 would do. The N+1 problem is the most common ORM performance bug. Fix it by loading related data together, with a JOIN or the ORM's include / populate.

    Keep queries in one layer

    Don't scatter prisma.user.findMany across route handlers. Put data access in a repository or service file. Then handlers stay small, and swapping or mocking the database for tests touches one place.

    Go deeperConnect your notes API to PostgreSQL with Prisma or Drizzle. Turn on query logging and count the queries per request.

    Authentication and authorization who are you, what can you do

    Authentication checks identity (login). Authorization checks permission (can this user delete this post?). Mixing them up is a classic source of security holes.

    Storing passwords: hash and salt

    Never store a password, not even encrypted. Store a hash: a one-way fingerprint. At login, hash what the user typed and compare. A salt is a random value mixed in per user, so two people with the same password get different hashes, and precomputed "rainbow tables" are useless.

    Real apps use bcrypt or argon2. They are slow on purpose, which makes guessing millions of passwords expensive. The demo below uses SHA-256 only to show what salting does.

    import bcrypt from "bcrypt";
const hash = await bcrypt.hash(password, 12);     // on signup
const ok = await bcrypt.compare(password, hash);  // on login

    The 12 is the cost factor. Each +1 doubles the work: cost 12 means 212 internal rounds, roughly 250 ms on a typical server. A user never notices that once at login, but it makes an attacker's billions of guesses thousands of times slower than a plain SHA-256. bcrypt stores the cost and salt inside the hash string ($2b$12$...), so you can raise the cost as hardware gets faster and old hashes still verify. Use the async functions, because hashing is CPU work that would block the event loop.

    Staying logged in: sessions or tokens

    Session cookieJWT
    What the client holdsA random session ID in a cookieA signed token containing user data
    What the server storesSession data, in a DB or RedisNothing, it just checks the signature
    Logging out a userDelete the session, doneHard: the token is valid until it expires
    Good forWebsites on one domainAPIs used by mobile apps and other services

    Both are fine. Sessions are simpler to get right. JWTs shine when many services must verify a user without a shared database.

    Inside a JWT

    A JWT is three base64url parts joined by dots: header, payload, signature. The payload is only encoded, not encrypted. Anyone can read it, so never put secrets in it. The signature, made with a secret only the server knows, proves the token was not edited. Paste or edit a token below:

    Where the browser keeps the token

    localStorage is easy, but any XSS script can read it and steal the token. An HttpOnly, Secure, SameSite cookie cannot be read by JavaScript, so it is the safer default for web apps. Mobile apps use the platform's secure storage.

    Access and refresh tokens

    A common JWT setup: a short-lived access token (around 15 minutes) sent with each request, and a long-lived refresh token stored in an HttpOnly cookie. When the access token expires, the client uses the refresh token to get a new one. The server can revoke refresh tokens, which fixes most of the logout problem.

    OAuth and "Sign in with Google"

    1. Your app redirects the user to Google.
    2. The user logs in there and approves.
    3. Google redirects back with a one-time code.
    4. Your server swaps the code for the user's profile, server to server.
    5. You create or find the user and start your own session.

    You never see their Google password. OpenID Connect is the identity layer on top of OAuth that makes this login flow standard.

    Authorization: roles and ownership

    const requireRole = (role) => (req, res, next) =>
  req.user.role === role ? next()
    : res.status(403).json({ error: "Forbidden" });

app.delete("/api/users/:id", requireAuth, requireRole("admin"), deleteUser);

    Also check ownership: a user may edit their own post, not anyone's. Forgetting this check (an IDOR bug) is one of the most common real-world vulnerabilities.

    Use a library or service

    Auth has many edge cases: password reset emails, email verification, 2FA, account lockout. Passport.js, Auth.js, Better Auth, Clerk, Supabase Auth and Firebase Auth cover them. Build it yourself once to learn, then use a proven tool in real projects.

    Security common attacks and fixes

    The OWASP Top 10 lists the attacks that hit real apps most often. Most of them come down to trusting input you should not trust.

    SQL injection

    If you glue user input into a SQL string, the input can change the query itself. Type something with a quote in it:

    Unsafe: string concatenation

    Safe: parameterized query

    The fix is always parameterized queries ($1, ?) or an ORM, which does that for you. The database then treats the input as plain data, never as SQL. NoSQL databases have their own version: never pass raw req.body objects into a MongoDB filter.

    XSS, cross-site scripting

    An attacker saves <script>...</script> as their username. If your site renders it as HTML, that script runs in every visitor's browser and can steal their session. Fixes: escape output (React does this by default), avoid innerHTML with user data, use HttpOnly cookies, and add a Content-Security-Policy header.

    CSRF, cross-site request forgery

    You are logged in to your bank. An evil page submits a hidden form to bank.com/transfer, and your browser attaches your cookie automatically. Fixes: SameSite=Lax or Strict cookies, CSRF tokens in forms, and never changing data on a GET.

    CORS, properly understood

    Browsers block a page on site-a.com from reading responses from api-b.com unless the API says it's allowed with Access-Control-Allow-Origin. For non-simple requests, like JSON POSTs or ones with an auth header, the browser first sends an OPTIONS "preflight" to ask.

    app.use(cors({ origin: "https://myapp.com", credentials: true }));

    CORS protects users in the browser. CORS is not API security, because curl and other servers ignore CORS completely. Don't "fix" errors with origin: "*" on an API that uses cookies.

    Rate limiting

    Limit how many requests one IP or user can make per minute. This slows password guessing, scraping and accidental loops in a client. Apply strict limits on login and signup, and looser ones elsewhere. Respond with 429 Too Many Requests and a Retry-After header that tells the client how long to wait. With several servers, keep the counters in Redis so every copy shares them.

    app.use("/api/auth", rateLimit({ windowMs: 60_000, limit: 5 }));

    Security headers

    helmet() sets a group of headers in one line: Content-Security-Policy (which scripts may run), Strict-Transport-Security (always use HTTPS), X-Content-Type-Options, and frame protection against clickjacking.

    Secrets and dependencies

    • Secrets live in environment variables or a secrets manager, never in Git. If one leaks, rotate it. Deleting the commit is not enough.
    • Run npm audit and keep packages updated. Most apps are mostly other people's code.
    • Give the database user only the permissions the app needs.
    • Don't log passwords, tokens or full card numbers.

    Don't leak details

    Stack traces, SQL errors and "user not found" versus "wrong password" all tell an attacker something. In production, return a generic message and log the details on the server. Login failures should say "email or password is wrong" either way.

    Project structure and architecture keeping it maintainable

    A 50-line server can live in one file. A real backend needs clear layers, so each file has one job and two people can work on it without stepping on each other.

    Layers

    src/
├── server.js       starts listening
├── app.js          creates app, adds middleware and routes
├── config/         reads and checks env variables
├── routes/         URL + method → controller
├── controllers/    read req, call a service, send res
├── services/       business rules ("can this order ship?")
├── repositories/   database queries
├── middleware/     auth, validation, errors
└── utils/          small shared helpers

    Requests flow down: route, controller, service, repository. Only controllers know about req and res. Only repositories know about the database.

    Why bother

    Services with no req/res can be tested with plain function calls and reused from a cron job or a queue worker. When you swap MongoDB for Postgres, only repositories change. When a bug says "wrong discount", you know to open services/.

    Folder-by-feature (users/, orders/, each with its own routes and service) works well once the app grows.

    Config in one place

    // config/index.js
const env = z.object({
  PORT: z.coerce.number().default(3000),
  DATABASE_URL: z.string().url(),
  JWT_SECRET: z.string().min(32),
}).parse(process.env);
export default env;

    Validate env variables at startup. A missing secret should crash immediately with a clear message, not fail at 2 a.m. on the first login.

    Custom error classes

    class AppError extends Error {
  constructor(status, message) {
    super(message);
    this.status = status;
    this.expose = true;
  }
}
throw new AppError(404, "Order not found");

    Services throw meaningful errors, and the single error middleware turns them into responses.

    Logging

    Use a logger like pino instead of console.log. Log as JSON with a level (info, warn, error) and a request ID, so you can follow one request through all its log lines. Logs are your only window into production.

    Monolith or microservices

    A monolith is one deployable app. Microservices split features into separate apps that talk over the network. Microservices let big teams deploy separately, but add network failures, data consistency problems and a lot of operational work. Start with a well-structured monolith. Split only when a real pain, like team size or one part needing very different scaling, demands it.

    TypeScript on the backend

    Types catch wrong field names and missing awaits before running. Recent Node versions can run .ts files directly by stripping the types, and tsx works on older ones. Shared types between frontend and backend are a big reason teams pick a Node backend.

    Performance and scaling more users, same speed

    Most speed problems come from the database or the network, not your JavaScript. Measure first, then cache, queue, or add servers.

    Caching

    A cache keeps the answer to an expensive question so the next ask is instant. Caches exist at every level: the browser (Cache-Control), a CDN near the user, your app's memory or Redis, and the database's own buffer. The hard part is invalidation, which means deciding when cached data is stale. A TTL (time to live) is the simplest answer.

    This is the cache-aside pattern: check the cache, on a miss read the database, then store the result with a TTL. When the user updates their profile, delete user:1 from the cache so nobody sees old data.

    Redis

    An in-memory key-value store that answers in under a millisecond. Backends use it for caching, sessions, rate-limit counters, leaderboards, pub/sub messages and job queues. Because it lives outside your Node process, every server copy shares it.

    Vertical and horizontal scaling

    Vertical: a bigger machine. Simple, but it has a ceiling and is one point of failure. Horizontal: more machines behind a load balancer that spreads requests across them. This only works if servers are stateless, with sessions and uploads stored elsewhere. Node's cluster mode or PM2 can also use every CPU core on one machine.

    Background jobs and queues

    Some work should not make the user wait: emails, PDFs, image resizing, calling slow third-party APIs. The request handler puts a job on a queue and responds right away. Separate worker processes take jobs off the queue, retry on failure, and can scale on their own.

    await emailQueue.add("welcome", { userId: user.id });
res.status(201).json(user);   // user doesn't wait for the email

    Tools: BullMQ (on Redis), RabbitMQ, AWS SQS, Kafka for very high volume.

    CDN

    A content delivery network copies static files and cacheable responses to servers around the world. A user in Chennai gets them from Chennai, not from a server in the US. Cloudflare, CloudFront and Vercel's edge network are common.

    Scaling the database

    In order: add the right indexes, fix N+1 queries, cache hot reads, add read replicas (copies that serve reads), and only much later shard (split data across databases). Most apps never need sharding.

    Measure before you fix

    Look at p95 latency (the slowest 5% of requests), not just the average. Use database slow-query logs, EXPLAIN, APM tools, and load testers like k6 or autocannon to find the real bottleneck.

    Go deeperSkim the Redis docs on strings and expiry. Then add Redis caching to one slow endpoint and measure before and after with autocannon.

    Real-time, files and integrations beyond request and response

    Not everything fits "client asks, server answers". Chat needs the server to push. Uploads need storage. Payments need webhooks.

    Getting updates to the client

    TechniqueHowGood for
    PollingClient asks "anything new?" every few secondsSimple dashboards; easy but wasteful
    Server-Sent EventsOne long HTTP response the server keeps writing toNotifications, live feeds, streaming AI text; one direction
    WebSocketsA persistent two-way connectionChat, multiplayer games, collaborative editing

    Socket.IO wraps WebSockets with rooms, reconnection and fallbacks. With several servers, connections are spread out, so you need Redis pub/sub or a hosted service (Pusher, Ably) to broadcast to everyone.

    File uploads

    Files arrive as multipart/form-data. multer parses them in Express. Don't store files in the database or on the server's disk, because servers get replaced. Use object storage like S3, Cloudflare R2 or Cloudinary, and save only the URL in the database.

    For big files, the server hands the client a short-lived presigned URL, and the browser uploads straight to storage. Always check file type and size on the server.

    Webhooks

    A webhook is another service calling your API when something happens: "payment succeeded" from Stripe, "push" from GitHub. Three rules:

    • Verify the signature header so nobody can fake events.
    • Respond 200 quickly, then process in a background job.
    • Handle duplicates, because providers retry. Store event IDs you have processed.
    app.post("/webhooks/stripe",
  express.raw({ type: "application/json" }),   // raw bytes, not parsed JSON
  (req, res) => {
    let event;
    try {
      event = stripe.webhooks.constructEvent(
        req.body, req.get("stripe-signature"), env.STRIPE_WEBHOOK_SECRET);
    } catch {
      return res.sendStatus(400);              // signature did not match
    }
    jobs.add("stripe-event", event);           // process later
    res.sendStatus(200);
  });

    The signature is computed over the exact bytes Stripe sent, so this route needs express.raw. If express.json parses the body first, verification always fails.

    Email and third-party APIs

    Send email through a provider (Resend, SendGrid, Amazon SES) instead of your own mail server, from a background job. When calling any outside API, set a timeout, retry with backoff, and assume it will sometimes be down.

    Scheduled jobs

    Cron jobs run on a schedule: nightly reports, clearing expired sessions, reminder emails. Use node-cron, BullMQ repeatable jobs, or your host's cron feature. With several servers, make sure only one runs each job.

    cron.schedule("0 2 * * *", cleanupExpiredSessions);  // 2:00 every day

    Calling AI models

    LLM APIs are just HTTP APIs with secret keys, so the call must come from your backend, never the browser. Responses can take seconds, so stream them to the client with SSE.

    Go deeperFollow the Socket.IO tutorial to build a tiny chat room, then add image messages uploaded to object storage.

    Testing change code without fear

    Tests are code that checks your code. They let you refactor, upgrade packages and merge each other's work while knowing nothing broke.

    Kinds of tests

    • Unit. One function alone, like a price calculator. Many of these, milliseconds each.
    • Integration. Several parts together, such as an endpoint hitting a real test database. The most valuable for APIs.
    • End-to-end. A real browser clicking through the full app (Playwright). Few of these, slowest.

    Testing an endpoint

    import request from "supertest";
import app from "../src/app.js";

test("rejects a bad email", async () => {
  const res = await request(app)
    .post("/api/users")
    .send({ name: "Eswar", email: "nope" });
  expect(res.status).toBe(400);
});

    Supertest calls your Express app without opening a port. That's one reason to export app separately from server.js.

    Tools

    Vitest or Jest run tests and assertions. Node also has a built-in runner (node --test). Supertest handles HTTP. Testcontainers or a Docker database gives each run a clean real database.

    Mocks and test data

    Mock what you don't control: payment providers, email, the clock. Don't mock what you are testing. Reset the database between tests so results never depend on order. Factories make test users and orders in one line.

    What to test first

    Money, permissions and anything that broke before. Test that a user cannot read another user's data. That single test catches a whole class of security bugs.

    Deployment and DevOps going live and staying up

    Deployment puts your server on a machine the internet can reach. DevOps is everything that keeps it running: automation, monitoring and recovery.

    Environments

    Development is your laptop. Staging is a production copy for final checks. Production serves real users. Same code everywhere, different config through environment variables. Set NODE_ENV=production, because many libraries run faster and hide error details in that mode.

    Where to host

    • Platform hosts (Render, Railway, Fly.io, Heroku): push code, they run it. Best way to start.
    • Serverless (Vercel, AWS Lambda, Cloudflare Workers): functions that run per request and scale to zero. No long-lived connections.
    • Virtual machines (AWS EC2, DigitalOcean): full control and full responsibility.
    • Containers (AWS ECS, Google Cloud Run, Kubernetes): run Docker images at scale.

    Docker

    A Docker image packages your app with its exact Node version and dependencies, so it runs the same on your laptop, CI and production. "Works on my machine" stops being a problem.

    FROM node:22-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev
COPY . .
EXPOSE 3000
CMD ["node", "src/server.js"]

    Docker Compose

    Compose starts your API, Postgres and Redis together with docker compose up. Every developer gets the same local setup without installing databases.

    # compose.yaml
services:
  api:
    build: .
    ports: ["3000:3000"]
    env_file: .env
    depends_on: [db, redis]
  db:
    image: postgres:17
    environment:
      POSTGRES_PASSWORD: dev
      POSTGRES_DB: notes
    volumes: ["pgdata:/var/lib/postgresql/data"]
  redis:
    image: redis:7
volumes:
  pgdata:

    Inside Compose, the API reaches the database by service name, not localhost: DATABASE_URL=postgresql://postgres:dev@db:5432/notes. The named volume keeps data when containers restart.

    CI/CD

    Continuous integration runs lint and tests on every push and pull request. Continuous deployment ships to production automatically when main passes. GitHub Actions is the usual choice for repos like this one. Migrations run as a step before the new version starts.

    Reverse proxy and HTTPS

    On a VM, Node usually sits behind Nginx or Caddy. The proxy handles HTTPS certificates, compression, static files and forwarding to Node on port 3000. Platform hosts do this for you. If you're behind a proxy, set app.set("trust proxy", 1) so Express sees the real client IP.

    Monitoring and health

    • A GET /health endpoint the host pings to restart dead servers.
    • Error tracking with Sentry, which alerts you with the stack trace.
    • Centralized logs and uptime alerts.
    • Database backups you have actually tested restoring.

    Graceful shutdown

    On every deploy, the host sends your process SIGTERM before replacing it. If you exit immediately, requests in progress are cut off and users see errors. Shut down in order instead:

    app.get("/health", (req, res) => res.json({ ok: true }));
const server = app.listen(env.PORT);

process.on("SIGTERM", () => {
  server.close(async () => {        // 1. stop accepting, finish open requests
    await prisma.$disconnect();      // 2. close DB and Redis connections
    process.exit(0);                 // 3. exit cleanly
  });
  setTimeout(() => process.exit(1), 10_000).unref();  // force quit if stuck
});

    Queue workers do the same: stop taking new jobs, finish the current one, then exit.

    How Next.js makes backend work easier full stack in one project

    Everything above assumed a separate Express server. Next.js lets the backend live inside the frontend project, which removes a lot of glue code for typical web apps.

    The idea

    In a classic setup you run two projects: a React app and an Express API. You deploy both, configure CORS between them, write fetch calls, and keep types in sync by hand. Next.js runs React on the server too, so a page can reach the database itself. When you do need an endpoint, it's a file in the same repo.

    Route handlers: Express routes as files

    // app/api/users/[id]/route.ts  →  /api/users/5
export async function GET(
  req: Request,
  { params }: { params: Promise<{ id: string }> }
) {
  const { id } = await params;
  const user = await db.user.findUnique({ where: { id: Number(id) } });
  if (!user) return Response.json({ error: "Not found" }, { status: 404 });
  return Response.json(user);
}

    Same concepts as Express: methods, params, status codes, JSON. The folder path replaces app.get(...).

    Server components read data directly

    // app/tasks/page.tsx (runs on the server)
export default async function TasksPage() {
  const tasks = await db.task.findMany();
  return <ul>{tasks.map(t => <li key={t.id}>{t.title}</li>)}</ul>;
}

    No API endpoint, no fetch, no loading spinner for the first paint. The database password never leaves the server because this code never ships to the browser.

    Server actions replace small POST endpoints

    // app/tasks/page.tsx
import { revalidatePath } from "next/cache";

async function addTask(formData: FormData) {
  "use server";                                   // runs on the server
  const title = String(formData.get("title") ?? "").trim();
  if (!title) return;                             // still validate!
  await db.task.create({ data: { title } });
  revalidatePath("/tasks");                       // refresh the page data
}

export default async function TasksPage() {
  const tasks = await db.task.findMany();
  return (
    <form action={addTask}>
      <input name="title" />
      <button>Add</button>
      <ul>{tasks.map(t => <li key={t.id}>{t.title}</li>)}</ul>
    </form>
  );
}

    The form calls a server function directly. Next.js creates the hidden endpoint for you. A server action is still a public endpoint underneath, so check auth and validate input in it exactly as you would in Express.

    What you gain

    • One repo, one language, one deploy.
    • No CORS, because frontend and backend share an origin.
    • Types flow from the database to the UI with no handwritten API types.
    • Fewer endpoints, because pages read data and forms call actions directly.
    • Built-in caching and revalidation for server data.
    • Middleware (called proxy in recent versions) for auth checks and redirects before a page loads.
    • Serverless hosting on Vercel scales up and down by itself.
    • Auth libraries (Auth.js, Clerk, Better Auth) plug in with a few files.

    When you still want Express

    • A public API for mobile apps and other teams, versioned on its own schedule.
    • Long-lived connections: WebSockets, game servers.
    • Long or heavy jobs. Serverless functions have time limits and cold starts.
    • In-memory state or background workers that must keep running.
    • Separate scaling, or a backend team working independently.

    Many real products use both: Next.js for the web app, and an Express service for the public API, workers and sockets.

    Side by side

    ConcernReact + ExpressNext.js
    Define an endpointapp.get("/api/users", fn)app/api/users/route.ts

    Everything from the earlier stages still applies inside Next.js: HTTP, databases, hashing, validation, security and caching. Next.js removes plumbing, not concepts.
