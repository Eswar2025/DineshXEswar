    How the web works the base for everything

    Every page you build is delivered the same way. Knowing the delivery route makes the rest easier to place.

    About 1 to 2 hours
    By the end you can
    • Describe what happens between typing a URL and seeing the page.
    • Name each part of a URL.
    • Find any request in the DevTools Network tab and read its status code.

    Request and response

    The browser is the client. It asks a server for something over HTTP, and the server answers. HTTPS is the same conversation, encrypted so nobody in between can read it.

    Think of a restaurant. You (the browser) give an order to the waiter, the kitchen (the server) prepares it, and the waiter brings back the dish (the response). Every page load, every image, and every button that loads data is one order.

    What happens when you open a URL

    1. DNS turns example.com into an IP address.
    2. The browser connects and sends a request.
    3. The server replies with HTML.
    4. The browser reads the HTML and asks for the CSS, JS and images it mentions.
    5. The browser renders the page.

    Parts of a URL

    https://example.com:443/blog/5?sort=asc#intro
protocol  domain     port path  query    fragment
    • Protocol: how to talk. Almost always https.
    • Domain: which server. DNS turns it into an IP address, like a phone book.
    • Port: which door on that server. Browsers hide it when it is the default (443 for https).
    • Path: which page or file.
    • Query: extra options as key=value pairs, joined with &.
    • Fragment: a spot on the page. It never goes to the server. This handbook's links, like #layout, are fragments.

    Methods and status codes

    Methods say what you want: GET read, POST create, PUT/PATCH update, DELETE remove.

    Status codes say what happened: 200 ok, 201 created, 301 moved, 400 bad request, 401 not logged in, 403 forbidden, 404 not found, 500 server error.

    How the browser renders

    HTML becomes the DOM tree. CSS becomes a style tree. The browser combines them, works out sizes and positions (layout), then draws pixels (paint). Changing layout is more costly than changing color, which matters later for animations.

    Frontend and backend

    Frontend is the code that runs in the browser: what users see and click. Backend runs on a server: logic, storage and security. They talk through APIs. Someone who does both is a full-stack developer.

    Practice and quick check

    Do these in your playground before you mark the stage learned. Type the code yourself; the typing is part of the learning.

    1. Watch a page load. Open any site, press F12, choose the Network tab, and reload. Find the first request, the HTML document. What is its status code? How many requests did the page make in total?
      Hint
      The first row is usually the page itself, with the type document. The total count is in the bar at the bottom of the Network tab.
    2. Cause a 404. Add a made-up path to a real site, like /this-page-does-not-exist. Find that request in Network and read its status.
      Hint
      Many sites still show a friendly page. The status code tells the truth, not the page design.
    3. Take a URL apart. Label every part of https://shop.example.com/products/42?color=blue&size=m#reviews.
      Show one answer
      Protocol https; domain shop.example.com; no port shown, so 443; path /products/42; query color=blue and size=m; fragment reviews.

    Quick check

    1. A request comes back with status 404. What happened?

    Codes starting with 4 mean the request had a problem. 404 is "not found". A crash is a 5xx code, and "not logged in" is 401.

    2. Which part of a URL is never sent to the server?

    The fragment, after #, is used only by the browser to jump to a spot on the page.

    3. After the HTML arrives, why does the browser make more requests?

    The HTML is only the starting point. Every stylesheet, script and image tag in it can trigger another request.

    HTML structure

    HTML says what is on the page: headings, paragraphs, images, links, forms. It is a markup language with no logic, only structure.

    About 3 to 4 hours
    By the end you can
    • Write a page skeleton from memory.
    • Choose semantic tags instead of div for headers, navigation, articles and footers.
    • Build a form where every input has a label and a name.

    Elements and attributes

    Most elements have an opening tag, content, and a closing tag. Void elements such as img and input have no closing tag or child content. Attributes add settings to the opening tag. 

    <a href="/about" class="link">About</a>
<img src="cat.png" alt="A sleeping cat">

    Page skeleton

    <!DOCTYPE html>
<html lang="en">
  <head>
    <meta charset="utf-8">
    <meta name="viewport" content="width=device-width, initial-scale=1">
    <title>My page</title>
    <link rel="stylesheet" href="style.css">
  </head>
  <body>...</body>
</html>

    The head holds metadata and resource links, including the title shown in the browser tab. The body holds the page content.

    Text, links and media

    Headings go from h1 to h6, like chapter and section titles in a book. Use one h1 per page and don't skip levels to get a smaller font. Size is CSS's job.

    <h1>Recipes</h1>
<h2>Breakfast</h2>
<p>Quick ideas for <strong>busy</strong> mornings.</p>
<a href="/recipes/dosa">Dosa recipe</a>
<a href="https://developer.mozilla.org" target="_blank" rel="noopener">MDN</a>
<img src="dosa.jpg" alt="A crispy dosa with chutney" width="400" height="300">

    href is where a link goes. alt describes an image for screen readers, and shows if the image fails to load. width and height let the browser reserve space before the image arrives, so the page doesn't jump.

    Lists and tables

    ul is a bullet list, ol is numbered, and each item is an li. Navigation menus are usually a ul of links.

    <ul>
  <li>Milk</li>
  <li>Bread</li>
</ul>

<table>
  <thead>
    <tr><th>Name</th><th>Score</th></tr>
  </thead>
  <tbody>
    <tr><td>Dinesh</td><td>8</td></tr>
    <tr><td>Eswar</td><td>9</td></tr>
  </tbody>
</table>

    tr is a row, th a heading cell, td a data cell. Use tables for data with rows and columns, never for page layout.

    Forms

    Forms are how users send data. Each input needs a name and a matching label. 

    <form action="/signup" method="post">
  <label for="email">Email</label>
  <input id="email" name="email" type="email" required>
  <button type="submit">Sign up</button>
</form>

    Other inputs: text, password, checkbox, radio, textarea, select.

    The browser checks required, minlength, pattern and type="email" before the form submits. That check is only for convenience, because the server must validate everything again.

    Semantic HTML

    Use tags that describe meaning: header, nav, main, section, article, aside, footer. Search engines and screen readers use them to understand the page. A pile of divs tells them nothing.

    Block and inline, id and class

    Block elements (div, p) take a full row. Inline elements (span, a) sit inside a line of text. An id must be unique on the page. A class can be reused anywhere, and it is what CSS mostly targets.

    Accessibility

    Write alt text for images, connect labels to inputs, keep headings in order, make everything reachable by keyboard, and keep enough color contrast. Reach for aria-* attributes only when no plain tag does the job.

    Common HTML mistakes

    • A div that acts like a button. Use <button>. It works with the keyboard and screen readers for free.
    • Headings picked by size. Choose the level by meaning, then change the size with CSS.
    • Inputs without labels. A placeholder is not a label. It disappears as soon as you type.
    • <br> for spacing. Use CSS margin or padding instead.
    • A missing alt. Describe the image, or write alt="" if it is only decoration.

    A button can be focused and pressed with the keyboard, and screen readers announce it as a button. A link is for going somewhere.

    Browser checks are a convenience. A user can edit the HTML in DevTools or send a request with no browser at all.

    3. Why use main, nav and footer instead of div?

    They look like plain divs until you style them. Their value is meaning: a screen reader user can jump straight to the main content.

    CSS basics style

    CSS controls how HTML looks: color, fonts, spacing and layout. A rule is a selector that picks elements and a list of property: value pairs.

    About 4 to 6 hours
    By the end you can
    • Explain which rule wins when two rules disagree.
    • Predict an element's real size from the box model.
    • Choose between px, rem and % for a value.

    Three ways to add CSS

    Inline with style="", internal in a <style> tag, or external in a .css file linked from the head. External is the normal choice because many pages can share one file.

    Selectors

    p { }              /* every p */
.card { }          /* class="card" */
#header { }        /* id="header" */
nav a { }          /* any a inside nav */
ul > li { }        /* direct children only */
a:hover { }        /* pseudo-class: a state */
p::first-line { }  /* pseudo-element: a part */

    Cascade and specificity

    When two rules set the same property on the same element, the browser has to pick one. For everyday CSS, three questions decide:

    1. Which selector is more specific? An id beats a class, and a class beats a tag name.
    2. Still a tie? The rule written later wins.
    3. Is it inline? A style="" attribute beats your stylesheet.
    p      { color: gray; }  /* 1 tag   */
.note  { color: blue; }  /* 1 class */
#intro { color: red;  }  /* 1 id    */

/* <p id="intro" class="note"> is red: the id wins. */

    Count ids first, then classes (pseudo-classes like :hover count as classes), then tags. !important jumps over all of this, which is why it starts fights. Avoid it.

    Some properties, like color and font-family, are inherited: children take the parent's value unless a rule sets their own.

    Later you will meet the full rules, such as style origins and @layer. You won't need them for a long time.

    The box model

    Every element is a box with four layers, from inside out: content, padding, border, margin. Most layout confusion comes from forgetting this. Set box-sizing: border-box so a width includes padding and border. Try it:

    content

    The dashed outline marks the margin, the solid border surrounds the box, and the tinted area between that border and the content is padding.

    Units

    UnitMeansGood for
    pxa fixed CSS pixelborders, small details
    remtimes the root font size, usually 16pxfont sizes, spacing
    emtimes this element's font sizepadding that grows with its text
    %a share of the parentwidths inside a container
    vw, vh1% of the window's width or heightfull-screen sections

    If someone raises their browser's default text size, rem sizes grow with it and px sizes don't. That makes rem the friendlier choice for text.

    Colors and typography

    Colors come as hex (#fffaf0), rgb() or hsl(). A good starting point for text:

    body {
  font-family: system-ui, sans-serif;  /* a fallback comes last */
  font-size: 1rem;                     /* 16px by default */
  line-height: 1.6;                    /* space between lines */
  color: #222;
}
h1 { font-size: 2.25rem; font-weight: 700; }

    A line-height of 1.5 to 1.7 reads well. Always end font-family with a generic fallback like sans-serif.

    Backgrounds, borders and shadows

    .card {
  background: white;
  border: 1px solid #ddd;
  border-radius: 12px;                     /* rounded corners */
  box-shadow: 0 2px 8px rgb(0 0 0 / 0.1);  /* soft depth */
  overflow: hidden;                        /* clip what spills out */
}

    overflow decides what happens when content is bigger than its box: visible lets it spill out (the default), hidden clips it, and auto adds scroll bars when needed.

    CSS variables

    :root { --brand: #0a0a0a; --gap: 16px; }
.card { background: var(--brand); padding: var(--gap); }

    Define a value once, reuse it everywhere. This page switches between dark and light by redefining a handful of variables.

    Common CSS mistakes

    • A typo fails silently. CSS skips a misspelled property or value without an error. DevTools marks it with a warning icon or a strikethrough.
    • Forgetting the dot. card { } looks for a <card> tag. A class needs .card { }.
    • The width surprise. By default, width: 300px plus 20px of padding is 340px wide. Start every project with *, *::before, *::after { box-sizing: border-box; }.
    • Fighting with !important. If a rule doesn't apply, find the rule that wins in DevTools and write a selector that matches or beats it.

    Quick check

    1. <p class="a" id="b"> has two rules: #b { color: blue }, then .a { color: red }. What color is it?

    An id is more specific than a class, so blue wins wherever the rules are written. Order only breaks ties.

    2. Which unit grows when a user raises their browser's default font size?

    rem is relative to the root font size, which follows the browser setting.

    3. Your CSS rule has no effect. Where do you look first?

    The Styles panel lists every rule that matched the element. Crossed out means another rule won. Missing means the selector didn't match.

    CSS layout placing things

    Once boxes look right, you arrange them. Modern layout is mostly flexbox, grid, and media queries.

    About 6 to 8 hours
    By the end you can
    • Pick flexbox or grid for a layout and say why.
    • Center anything in both directions.
    • Make a page that works from phone width to desktop.

    display

    block takes a full row, inline flows in text, inline-block flows but accepts width and height, none removes the element. flex and grid turn an element into a layout container.

    position and z-index

    Normally boxes sit in the flow, one after another like words in a paragraph. position lets you nudge a box or lift it out of that flow.

    position: static;    /* default, normal flow */
position: relative;  /* nudged from its own spot */
position: absolute;  /* placed inside the nearest positioned ancestor */
position: fixed;     /* stuck to the screen */
position: sticky;    /* normal, then sticks while scrolling */

    The one that confuses everyone: absolute is measured from the nearest ancestor whose position isn't static. That's why you often see position: relative on a parent with no offsets. It's there to be the anchor. Try each value:

    Flexbox

    Flexbox lays items out along one line, a row or a column. That line is the main axis. The other direction is the cross axis.

    • justify-content spreads items along the main axis.
    • align-items lines them up on the cross axis.
    • Switch to column and the two swap directions. Try it below.

    Three more you will use all the time:

    .item { flex: 1; }          /* items share the free space equally */
.logo { flex: none; }       /* keep its own size, never shrink */
.row  { flex-wrap: wrap; }  /* move to a new line when out of room */

    Use it for navbars, button groups, and anything in a single row or column.

    Grid

    Grid places items in rows and columns at the same time. You describe the columns on the parent, and the children fill the cells in order.

    .gallery {
  display: grid;
  grid-template-columns: repeat(3, 1fr);  /* 3 equal columns */
  gap: 16px;
}
.featured { grid-column: span 2; }        /* this item takes 2 columns */

    fr means "a share of the free space". The most useful line in grid is repeat(auto-fit, minmax(200px, 1fr)): as many columns as fit, each at least 200px wide. It's responsive without a single media query. Shrink the container and watch:

    Responsive design

    The same page has to work on a phone, a tablet and a desktop. You need the viewport meta tag, flexible units, and media queries. Start from the phone layout and add rules for larger screens (mobile-first). 

    .cards { display: grid; gap: 16px; grid-template-columns: 1fr; }
@media (min-width: 768px) {
  .cards { grid-template-columns: repeat(3, 1fr); }
}

    clamp(16px, 2.5vw, 22px) gives a size that grows with the screen but never goes below the minimum or above the maximum. Heading sizes are the usual use.

    Centering, the common recipe

    .parent {
  display: flex;
  justify-content: center;
  align-items: center;
  min-height: 100vh;
}

    When layout goes wrong

    Three tricks solve most layout puzzles:

    1. Outline everything for a minute. * { outline: 1px solid red; } shows every box. Unlike a border, an outline takes no space, so it doesn't change the layout.
    2. Use the DevTools badges. In Elements, click the flex or grid badge next to an element to draw its lines and gaps on the page.
    3. Hunt the sideways scroll. A page that scrolls sideways on a phone has one element wider than the screen: a fixed width, a long URL, an image without a max width, or 100vw plus a scroll bar.
    img { max-width: 100%; height: auto; }  /* images never overflow */

    It's one direction, a row, which is flexbox's job. Absolute positioning breaks as soon as the text or screen size changes.

    Transforms and motion movement

    Transforms move, rotate and scale an element. Transitions and animations spread a change over time.

    About 2 to 3 hours
    By the end you can
    • Add smooth hover effects with transitions.
    • Build a looping animation with keyframes.
    • Keep animations smooth and respect reduced motion.

    transform

    translate moves, rotate turns, scale resizes, skew slants. A transform does not change the layout, so neighboring elements stay where they are. The dashed box below is the original position. Order matters, because each step happens in the already transformed space.

    box

    transition

    Tells the browser to animate a property change instead of jumping. You give it the property, duration, easing and optional delay. 

    .btn { transition: transform 200ms ease, background 200ms ease; }
.btn:hover { transform: translateY(-2px); }

    @keyframes and animation

    When you need more than a start and an end, or something that loops, describe the steps in @keyframes and attach them with animation. 

    @keyframes pulse { from { opacity: 1 } to { opacity: .4 } }
.dot { animation: pulse 1s ease-in-out infinite alternate; }

    Keeping it smooth

    Prefer animating transform and opacity: these usually avoid layout and can be handled by compositing. GPU acceleration depends on browser decisions and is not guaranteed. Animating width, height, top or left can trigger repeated layout and cause stutter. Check the browser performance tools when an animation is slow.

    3D basics

    Add perspective to a parent and rotate the child on rotateX or rotateY for card flips and tilt effects.

    .scene { perspective: 800px; }
.card  { transition: transform 0.6s; }
.scene:hover .card { transform: rotateY(180deg); }

    Reduced motion

    Some people get dizzy or sick from motion on screen. Operating systems have a "reduce motion" setting, and CSS can read it:

    @media (prefers-reduced-motion: reduce) {
  * { animation: none !important; transition: none !important; }
}

    This is one of the rare good uses of !important: it has to win over every other rule.

    Practice and quick check

    Do these in your playground before you mark the stage learned. Type the code yourself; the typing is part of the learning.

      Hint
      Put transition on the button's normal rule, not on :hover, so it animates both ways. Move it with transform, not top.
    2. A loading spinner. A circle with one colored edge that spins forever, in pure CSS.
      Hint

    Quick check

    1. Which is smoother to animate?

    Changing left makes the browser redo layout on every frame. transform usually skips layout and paint.

    2. A hover effect animates when the mouse enters but snaps back instantly when it leaves. Why?

    When the mouse leaves, the :hover rule stops applying, and its transition goes with it. Put the transition on the base rule.

    3. When do you need @keyframes instead of a transition?

    A transition only animates between two states when something changes. Keyframes describe a whole sequence.

    JavaScript behavior

    JavaScript is the programming language of the browser. It reacts to clicks, checks forms, fetches data and changes the page without a reload. It also runs on servers through Node.js.

    About 12 to 15 hours
    By the end you can

    • Explain the difference between copying a value and sharing a reference.

    Variables and types

    A variable is a name for a value. Use const by default and let only when you will reassign it. Skip var, the old way with confusing scope rules.

    const name = "Eswar";   // string
let score = 0;          // number: whole and decimal alike
score = score + 10;     // fine, it's let
const done = false;     // boolean
let picked = null;      // "nothing, on purpose"
let city;               // undefined: "not set yet"

const tasks = [];       // an array is an object
tasks.push("learn JS"); // allowed: the array changes, the name doesn't

    The simple types are string, number, boolean, null and undefined (plus bigint and symbol, which you'll rarely meet). Everything else, including arrays and functions, is an object.

    Compare with ===, which never converts types: "5" == 5 is true, but "5" === 5 is false.

    Strings and numbers

    const msg = "  Hello, World  ";
msg.trim();               // "Hello, World"
msg.toLowerCase();        // "  hello, world  "
msg.includes("World");    // true
"a,b,c".split(",");       // ["a", "b", "c"]
`Total: ${2 + 3}`;        // "Total: 5"

Number("42");             // 42
Number("42px");           // NaN, "not a number"
parseInt("42px", 10);     // 42
(19.999).toFixed(2);      // "20.00", a string

    Two surprises to know early. "5" + 1 is "51", because + joins text when either side is a string. And 0.1 + 0.2 is 0.30000000000000004, because computers store decimals in binary. For money, count whole paise or cents.

    Functions

    A function is a reusable recipe: inputs (parameters) go in, and a result comes out with return. Functions are values too, so you can store them and pass them to other functions.

    function add(a, b) { return a + b; }
const add2 = (a, b) => a + b;                    // arrow function
const greet = (name = "friend") => `Hi ${name}`; // default value

greet();                          // "Hi friend"
[1, 2, 3].map(n => add(n, 10));   // pass a function in: [11, 12, 13]

    Arrow functions are shorter and don't have their own this (see the this keyword). A function without return gives back undefined, the cause of many "why is it undefined?" moments.

    Arrays and objects

    Your two main data structures. An array is an ordered list. An object is a set of named values. Real data is usually an array of objects:

    const tasks = [
  { id: 1, title: "HTML page",    done: true,  mins: 40 },
  { id: 2, title: "Flexbox game", done: false, mins: 25 },
  { id: 3, title: "Array drills", done: false, mins: 30 },
];
tasks[0].title;          // "HTML page"
tasks.length;            // 3
Object.keys(tasks[0]);   // ["id", "title", "done", "mins"]

    Pick a method to see what it returns on that array. These six cover most real code.

    Control flow

    if (score >= 90) grade = "A";
else if (score >= 75) grade = "B";
else grade = "C";

for (const task of tasks) console.log(task.title);    // arrays
for (const [key, value] of Object.entries(user)) {}   // objects

const label = done ? "Done" : "To do";                // a short if/else

    Conditions treat some values as false: false, 0, "", null, undefined and NaN (plus the rare -0 and 0n). Everything else counts as true, including empty arrays and objects.

    Scope and closures

    Scope determines where a binding can be accessed. let and const are block-scoped; var is function-scoped. Inner functions can access bindings in their outer scopes. A closure is a function that retains access to its surrounding lexical environment. 

    function counter() { let c = 0; return () => ++c; }
const next = counter();
next(); // 1
next(); // 2

    Why it matters. Closures give you private data: nothing outside counter can touch c. They let an event handler remember which item it was created for. Every React hook depends on them. They also cause the "stale closure" bug, where a function created during an old render still sees old values. If a timer inside useEffect keeps printing an old count, this is why.

    Copying: values and references

    Simple values are copied. Objects and arrays are shared: the variable holds a reference, like a home address, not the house itself.

    let a = 5;
let b = a;
b = 10;
a;                      // 5, numbers are copied

const user = { name: "Dinesh" };
const same = user;      // the same address
same.name = "Eswar";
user.name;              // "Eswar", one object, two names

const copy = { ...user, name: "Priya" };  // a new object
const more = [...list, newItem];          // a new array

    This explains two things you'll meet soon: why {} === {} is false (two different objects), and why React wants a new array or object when state changes. Spread copies one level deep; structuredClone(obj) copies everything.

    Modern syntax (ES6+)

    const { name, age } = user;            // destructuring
const all = [...a, ...b];              // spread
const city = user?.address?.city;      // optional chaining
console.log(`Hi ${name}`);             // template string
import { add } from "./math.js";       // modules

    The this keyword

    this is decided when a function is called, not where it is written. The rules:

    • obj.method(): this is obj.
    • A plain call fn(): undefined in modules and strict mode.
    • Arrow functions have no this of their own. They use the one from the code around them.
    • A normal-function event listener: this is the element.
    • bind, call and apply set it by hand. 
    const user = {
  name: "Eswar",
  hi() { return this.name; },
  later() { setTimeout(() => console.log(this.name), 100); },
};
user.hi();                    // "Eswar"
const f = user.hi; f();       // error: this is undefined
user.hi.bind(user)();         // "Eswar"
user.later();                 // "Eswar", the arrow keeps this

    The classic bug is passing user.hi as a callback and losing this. An arrow function or bind fixes it.

    Classes

    A class is a blueprint for objects, with a constructor that sets them up and methods they share. You'll see classes in older React code, in Node libraries, and in custom error types. Modern React uses functions instead.

    class Timer {
  constructor(label) { this.label = label; this.seconds = 0; }
  tick() { this.seconds++; }
}
const t = new Timer("focus");
t.tick();   // t.seconds is now 1

    Errors and JSON

    JSON is text that looks like a JavaScript object. It's how the frontend and backend send data to each other. Keys need double quotes, and it can't hold functions or undefined.

    const text = JSON.stringify({ name: "Dinesh", done: true });
// '{"name":"Dinesh","done":true}'
const obj = JSON.parse(text);          // back to an object

try {
  JSON.parse("{ name: 'oops' }");      // not valid JSON
} catch (error) {
  console.error("Could not read it:", error.message);
}

    try runs code that might fail, and catch receives the error so the page keeps working. Raise your own with throw new Error("message").

    What the DOM is

    Debounce and throttle

    Some events fire dozens of times a second: input, scroll, resize. Running heavy work on each one makes the page lag and floods the server.

    • Debounce waits until the events stop for a moment, then runs once. Use it for search-as-you-type, so typing "react" sends one request instead of five.
    • Throttle runs at most once per interval while events keep coming. Use it for scroll position or infinite scroll. 
    function debounce(fn, ms) {
  let t;
  return (...args) => {
    clearTimeout(t);
    t = setTimeout(() => fn(...args), ms);
  };
}
input.addEventListener("input", debounce(search, 300));

    This is a closure at work: t survives between calls.

    Async JS and fetch talking to servers

    Network calls take time. Asynchronous code lets the page stay responsive while it waits.

    About 6 to 8 hours
    By the end you can

    • Fetch JSON with async/await and handle errors properly.
    • Show loading, empty, error and success states.

    The event loop

    JavaScript does one thing at a time. When it starts something slow, like a request or a timer, it hands the job to the browser and keeps going. When the job finishes, the callback joins a queue and runs when the main code is free. Think of a waiter who takes your order and serves other tables while the kitchen cooks.

    Node.js uses a similar event-loop model on the server, with its own phases and scheduling details. The Backend handbook has a live demo of the order that callbacks run in.

    Predict what this prints, then run it:

    console.log("1. start");
setTimeout(() => console.log("timeout"), 0);
Promise.resolve().then(() => console.log("promise"));
console.log("2. end");
    Press the button. The page runs the code above and logs each line here.

    All normal code runs first. Then promise callbacks (microtasks). Then timers, even with a 0ms delay.

    Callbacks, promises, async/await

    Callbacks came first and nested badly. Promises fixed that with .then(). async/await reads like normal top-to-bottom code and is what you should write. 

    // promise style
fetch("/api/users")
  .then(r => r.json())
  .then(users => console.log(users))
  .catch(err => console.error(err));
    // async/await, same thing
async function load() {
  try {
    const res = await fetch("/api/users");
    if (!res.ok) throw new Error(res.status);
    const users = await res.json();
  } catch (err) {
    // show an error message
  }
}

    Running requests in parallel

    // one after another: about 2 seconds
const user = await getUser();
const posts = await getPosts();

// at the same time: about 1 second
const [u, p] = await Promise.all([getUser(), getPosts()]);
    • Promise.all fails as soon as one promise fails.
    • Promise.allSettled waits for every promise and reports each result, success or failure.
    • Promise.race settles with whichever finishes first. Racing a request against a timer can implement a timeout result, but does not cancel the request; use an AbortController when cancellation is needed.

    Only run requests in parallel when neither needs the other's result.

    fetch

    fetch sends HTTP requests from the browser. For a POST, send JSON in the body and say so in the headers. 

    await fetch("/api/tasks", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ title: "Learn DOM" }),
});

    Working with APIs

    An HTTP API exposes endpoints that clients can call to read data or perform actions, often using JSON. Handle loading, success, empty and error states in the UI. CORS controls whether browser JavaScript may read responses from another origin; some requests also need a successful preflight before being sent. It is not server-side permission checking. The Backend CORS card explains the distinction, and its REST stage covers API design.

    Loading, empty, error, success

    Every screen that fetches data is always in one of four states. Beginners build only "success", so the page looks broken while it loads or when the network fails. Pick a scenario:

    The code shape that handles all four:

    async function loadTasks() {
  render({ status: "loading" });
  try {
    const res = await fetch("/api/tasks");
    if (!res.ok) throw new Error(`HTTP ${res.status}`);
    const tasks = await res.json();
    render(tasks.length ? { status: "success", tasks } : { status: "empty" });
  } catch (error) {
    render({ status: "error", message: "Couldn't load tasks. Try again." });
  }
}

    Timers

    setTimeout(fn, ms) runs once later. setInterval(fn, ms) repeats until you call clearInterval. Always clear intervals you no longer need.

    Common mistakes

    • Forgetting await, so you hold a promise instead of data.
    • Not checking res.ok. A 404 does not throw.
    • No error handling, so the UI hangs on "loading".

    Debugging when it doesn't work

    Developers spend a large part of every day with code that doesn't work yet. Debugging is a skill with steps, not luck, and it gets faster with practice.

    About 2 to 3 hours, then every day after
    By the end you can
    • Read an error message and jump to the line that caused it.
    • Narrow down a bug with console.log and breakpoints.
    • Ask for help with a small, clear example.

    A debugging routine

    1. Reproduce it. Find the exact steps that make it happen every time.
    2. Read the error. All of it, including the file name and line number.
    3. Check your assumptions. Log the values you are "sure" about. One of them is usually wrong.
    4. Narrow it down. Log at each step, or comment out half the code, until you find the first place where reality differs from what you expected.
    5. Change one thing at a time, then test again.
    6. Explain the fix. If you can't say why it works, you may have hidden the bug instead of fixing it.

    Reading error messages

    An error message tells you the type, the reason, and where it happened. Click the file link on the right of the Console message to jump to the line.

    Uncaught TypeError: Cannot read properties of null (reading 'addEventListener')
    at script.js:4:8

    Read it as: on line 4 of script.js, something was null, and the code tried to call addEventListener on it. Look at whatever comes before the dot.

    ErrorWhat it usually means
    Cannot read properties of null or undefinedSomething you expected doesn't exist: querySelector found nothing, or data hasn't loaded yet.
    ReferenceError: x is not definedA typo in a name, or a variable used outside its scope.
    TypeError: x is not a functionA typo like getElementByID, or calling something that is data, not a function.
    SyntaxError: Unexpected tokenA missing bracket, comma or quote, often on the line before the one reported.
    Unexpected token '<' while reading JSONYou called res.json() on an HTML page, often a 404 page from a wrong URL.
    Uncaught (in promise)An async function threw and nothing caught it. Wrap the await in try and catch.
    Failed to fetch or a CORS errorThe request was blocked or never reached the server. Check the URL, the Network tab, and the Backend CORS card.

    React components, props, state

    Plain DOM code gets messy as pages grow. React lets you describe what the UI should look like for the current data, and it updates the DOM for you.

    About 8 to 10 hours
    By the end you can
    • Split a screen into components and pass data down with props.
    • Keep changing data in state and update it without mutating it.
    • Render lists with keys, and show different UI for different states.

    The core idea

    UI is a function of state. Change the data, and React redraws the parts that depend on it.

    You stop writing "find this element and change its text". You write what the screen should show, and update the data.

    Thinking in React

    Before writing code, plan on paper. React's own docs suggest these steps:

    1. Draw boxes around the UI. Each box with one job is a component.
    2. Build a static version with props only and no state, so it just displays data.
    3. Find the smallest state. For each piece of data ask: does it change over time? Can it be calculated from something else? If it can be calculated, it isn't state.
    4. Decide where state lives: in the closest common parent of every component that needs it.
    5. Pass functions down so children can ask that parent to change it.
    TaskApp              state: tasks, filter
├── AddTaskForm      gets onAdd
├── FilterTabs       gets filter, onChange
└── TaskList         gets the visible tasks
    └── TaskItem     gets task, onToggle, onDelete

    In this to-do app the visible list isn't state. It's calculated from tasks and filter on every render.

    State

    State is data a component owns that changes over time. Why not a normal variable? A normal variable resets on every render, and changing it doesn't tell React to redraw. A state setter does both: it keeps the value and triggers a re-render.

    import { useState } from "react";

function Counter() {
  const [count, setCount] = useState(0);
  return (
    <button onClick={() => setCount(count + 1)}>
      Clicked {count}
    </button>
  );
}

    Two rules that trip up everyone:

    • Never mutate state. tasks.push(t) edits the old array, so React may not notice. Make a new one: setTasks([...tasks, t]). See values and references.
    • The new value isn't there yet. Right after setCount(count + 1), count still holds the old number. It changes on the next render.

    Events and forms

    Handlers are props like onClick and onChange. A controlled input keeps its value in state, so the state is the single source of truth. 

    <input value={name} onChange={e => setName(e.target.value)} />

    One-way data flow

    Data goes down through props. Changes go up through functions passed as props. When two components need the same data, move the state to their nearest common parent. This is called lifting state up.

    React hooks giving components abilities

    Hooks are functions that start with use. They let a function component hold state, run side effects, and share logic.

    About 8 to 10 hours
    By the end you can
    • Tell when an effect is needed and when it isn't.
    • Fetch data in an effect, with cleanup.
    • Move repeated logic into a custom hook.

    The two rules

    • Call hooks at the top level of a component, never inside an if, loop or nested function.
    • Call them only from components or from your own hooks.

    React tracks hooks by call order, so the order must never change.

    useState

    Local state can trigger a re-render when updated. The hook returns the current value and a setter. When the next value depends on the previous one, use a functional update, such as setItems(items => [...items, newItem]). Copy objects and arrays instead of mutating existing state. React may skip an update when the next value is equal by Object.is.

    useEffect

    An effect synchronizes a component with an external system, such as a request, timer or event subscription. React runs it after a render commits; effects do not run during server rendering. The dependency array controls when setup is repeated. Each reactive value used by the effect belongs in that array.

    Dependency array Effect runs
    useEffect(fn) after every committed render
    useEffect(fn, []) on mount; cleanup on unmount (see Strict Mode below)
    useEffect(fn, [id]) on mount, then after commits where id changes

    The first version you'll write looks like this:

    useEffect(() => {
  fetch("/api/users")
    .then(res => res.json())
    .then(data => setUsers(data));
}, []);   // run once, after the first render

    It works, but it has two holes: no error handling, and a late response can still set state after the component is gone or the request was replaced. The safe version below fixes both. Read it once now, and again after you've written the simple one.

    // setUsers and setError are component state setters.
useEffect(() => {
  const controller = new AbortController();
  let ignore = false;
  setError(null);
  async function load() {
    try {
      const res = await fetch("/api/users", { signal: controller.signal });
      if (!res.ok) throw new Error(`HTTP ${res.status}`);
      const users = await res.json();
      if (!ignore) setUsers(users);
    } catch (error) {
      if (!ignore && error.name !== "AbortError") setError(error);
    }
  }
  load();
  return () => { ignore = true; controller.abort(); };
}, []);
    useEffect(() => {
  const id = setInterval(tick, 1000);
  return () => clearInterval(id);
}, [tick]); // restart if the tick function changes

    Cleanup runs before setup repeats with changed dependencies, and on unmount. In development, Strict Mode also performs an extra setup/cleanup cycle to find missing cleanup. The request example cancels work and ignores stale results. An effect captures the values from its render, so omitted dependencies can produce stale closures. These are JavaScript excerpts; import the hooks and define the surrounding component state. React's effect reference explains the lifecycle.

    You might not need an effect

    Effects are for talking to things outside React: the network, timers, the browser tab. A common beginner habit is using an effect to calculate data. That costs an extra render and leaves values out of sync for a moment.

    // avoid: an effect that copies state
const [visible, setVisible] = useState([]);
useEffect(() => {
  setVisible(tasks.filter(t => !t.done));
}, [tasks]);
    // better: calculate during render
const visible = tasks.filter(t => !t.done);

    The same goes for user actions: respond to a click inside the click handler, not in an effect that watches state. React's guide You Might Not Need an Effect has many more examples.

    useRef

    Holds a value that survives renders without causing one. The usual job is grabbing a DOM element. 

    const inputRef = useRef(null);
<input ref={inputRef} />
<button onClick={() => inputRef.current.focus()}>Focus</button>

    useContext

    Shares data with many components without passing props through every level (prop drilling). Good for the theme, the current user, or the language.

    React.memo, useMemo and useCallback

    A parent update normally causes React to render its child components, though memoization and reuse can avoid some work. Rendering does not necessarily change the DOM. If rendering is measurably expensive:

    • React.memo(Component) can skip rendering when props compare equal. Its own state or a consumed context can still cause rendering; memoization is a performance optimization, not a correctness guarantee.
    • useMemo remembers a calculated value until its dependencies change.
    • useCallback remembers a function, so a memoized child does not receive a "new" function every render. 
    const Row = React.memo(function Row({ item, onSelect }) { /* ... */ });

const sorted = useMemo(() => sortItems(items), [items]);
const onSelect = useCallback(id => setSelected(id), []);

    All three are speed tweaks. Measure with the React DevTools Profiler first. The React Compiler can add most of this automatically in newer setups.

    useReducer

    An alternative to useState when one piece of state changes in many ways. You send actions like "add" or "toggle" to one function that decides the next state.

    function reducer(tasks, action) {
  switch (action.type) {
    case "add":    return [...tasks, action.task];
    case "toggle": return tasks.map(t =>
                     t.id === action.id ? { ...t, done: !t.done } : t);
    case "remove": return tasks.filter(t => t.id !== action.id);
    default:       return tasks;
  }
}
const [tasks, dispatch] = useReducer(reducer, []);
dispatch({ type: "toggle", id: 3 });

    Custom hooks

    Your own function starting with use that bundles other hooks, so logic can be reused. 

    import { useEffect, useState } from "react";

function useFetch(url) {
  const [result, setResult] = useState({
    data: null, error: null, loading: true,
  });

    const controller = new AbortController();
    let ignore = false;

        if (!res.ok) throw new Error(`HTTP ${res.status}`);
        const data = await res.json();

      } catch (error) {
        if (!ignore && error.name !== "AbortError") {
          setResult({ data: null, error, loading: false });
        }
      }
    }
    load();
    return () => { ignore = true; controller.abort(); };
  }, [url]);
  return result;
}

    JSX vs TSX adding types

    TSX is JSX written in TypeScript. The React you learned stays the same. You only add types.

    What TypeScript is

    TypeScript adds static types to JavaScript. An editor or the TypeScript checker can detect type mismatches before execution. Build tools remove the types to produce JavaScript, but merely stripping types does not check them. Keep a type-check step such as tsc --noEmit in development or CI. Types do not validate incoming JSON at runtime; use a runtime schema for that. 

    function add(a: number, b: number): number { return a + b; }
add("1", 2);   // error while coding

    The difference

    .jsx .tsx
    Language JavaScript + markup TypeScript + markup
    Types None Yes, checked
    Markup like <div> allowed Yes Yes
    Runs in browser as JavaScript The same JavaScript, types removed

    A plain .ts file cannot contain markup, so any component with TypeScript goes in a .tsx file. Files with no markup, like utilities, stay .ts. Here is the same component both ways: 

    // Card.jsx
function Card({ title, count = 0 }) {
  return <h3>{title} ({count})</h3>;
}
    // Card.tsx
interface CardProps {
  title: string;
  count?: number;   // optional
}
function Card({ title, count = 0 }: CardProps) {
  return <h3>{title} ({count})</h3>;
}

    What it is and why it exists

    A client-rendered React SPA often starts with a small HTML shell and builds its UI in the browser. That can delay meaningful content and make indexing harder for some crawlers.     Rendering strategies

    The big idea in Next.js is choosing where and when the HTML is made.

    Name HTML is made Good for
    SSR, server-side rendering on the server, per request fresh data, dashboards, SEO

    CSR, client-side rendering in the browser, often after an initial HTML response highly interactive widgets

    Server and client components

    In the App Router, pages and layouts are Server Components by default. Their implementation runs on the server and is not shipped as component JavaScript to the browser. They can read a database and render Client Components. A "use client" directive marks a client-module boundary for state, effects and event handlers; imports below that boundary join the client bundle.

    Hydration makes pre-rendered HTML interactive by connecting it to React in the browser. Client Components can also contribute server-rendered HTML on the initial load; "use client" does not mean browser-only execution. Keep browser APIs such as window in effects or event handlers. A subtree can still ship client JavaScript even when its parent is a Server Component.

    How frontend and backend meet

    Follow one click in a to-do app through the whole stack. Each step links to where it is explained.

    1. The user types a task and presses Add. A React event handler runs and updates state.
    2. The handler calls fetch("/api/tasks", { method: "POST" }) with the task as JSON.
    3. The request crosses the network as HTTP, and CORS applies if the API lives on another origin.
    4. Express runs its middleware: parse the JSON, check the login cookie, validate the body.
    5. A service saves the task in the database.
    6. The server replies 201 Created with the saved task.
    7. Back in the browser, the new task goes into state and React re-renders the list.

    With Next.js, steps 2 to 6 can shrink into one server action, but the same things still happen underneath.

    Glossary

    New words, in plain English. Each one links to the card that explains it.

    API
    A set of URLs a server offers so other code can read or change data.
    Async
    Code that starts now and finishes later, without freezing the page.
    Attribute
    A setting in an opening HTML tag, like href or alt.
    Breakpoint
    A spot where DevTools pauses your code so you can inspect it.
    Bubbling
    An event travelling up from the clicked element through its parents.
    Bundler
    A tool that combines many source files into a few for the browser.
    Cascade
    The rules that decide which CSS declaration wins.
    Closure
    A function that remembers the variables around where it was created.
    Component
    A function that returns a piece of UI in React.
    CORS
    Browser rules about reading responses from another origin.
    Debounce
    Waiting until events stop for a moment before running code once.
    Dependency array
    The list that tells React when to run an effect again.
    DOM
    The live tree of objects the browser builds from your HTML.
    Effect
    Code that syncs a React component with something outside React.
    Event
    Something that happens on the page, like a click or a key press.
    fetch
    The browser function for sending HTTP requests.
    Flexbox
    A CSS layout for items along one row or column.
    Grid
    A CSS layout for rows and columns at once.
    Hook
    A React function starting with use that gives components abilities.
    Hydration
    React attaching event handlers to HTML that was rendered on the server.
    JSON
    A text format for data, shaped like JavaScript objects.
    JSX
    HTML-like syntax inside JavaScript, used by React.
    Media query
    A CSS rule that applies only at certain screen sizes or settings.
    Mutate
    To change an existing object or array in place.
    npm
    The tool that installs JavaScript packages and runs project scripts.
    Promise
    An object standing for a value that will arrive later, or an error.
    Props
    Inputs a parent component passes to a child.
    Reference
    What a variable holds for objects and arrays: the address, not a copy.
    Render
    React calling your component to work out what the screen should show.
    Responsive
    A layout that adapts to the screen size.
    Semantic HTML
    Tags chosen for meaning, like nav and main.
    Server Component
    A Next.js component that runs only on the server.
    Specificity
    The score that decides which CSS selector is stronger.
    SPA
    Single page app: one HTML page that swaps views with JavaScript.
    State
    Data a component owns that changes over time.
    Status code
    The number in a response that says how a request went, like 200 or 404.
    TypeScript
    JavaScript with types that are checked while you code.

    The visible area of the page in the browser window.
