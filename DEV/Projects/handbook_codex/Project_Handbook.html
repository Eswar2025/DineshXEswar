The project roadmap

Follow the decisions

Start with a problem, choose a small slice, model its rules, and trace it through the stack. Expand the roadmap to jump to a chapter or one of its connected topics.

    01 / The first conversation

    Start with the problem

    Before choosing libraries, decide whose work you are making easier. Our fictional product is Traceboard: an issue tracker for a small project team.

    Listen for a broken workflow

    Bugs are scattered across chat. Nobody knows who is working on them, and a fixed bug gets reported again. The need is a shared record with ownership, discussion and a visible status.

    Decision. Build a reliable place to report and follow an issue. A beautiful board alone does not solve missing permissions or lost data.

    Write one concrete story

    An editor opens a project, reports “Fix the mobile navbar”, and sees the saved issue. Another editor adds a comment. A viewer can follow the discussion but cannot edit it.

    That small story gives us screens, requests, rules and database records. It is more useful than starting with a list of technologies.

    Define observable success

    • An authorized editor can create an issue and retrieve it after a reload.
    • A viewer cannot create an issue by calling the API directly.
    • A user outside the project cannot see its issues.
    • A failed save shows an error and preserves the typed text.

    Turn assumptions into questions

    • Are projects private? Yes, only active members can access them.
    • Can viewers comment? In this case study, no.
    • Can an issue belong to two projects? No.
    • Do we need live updates immediately? No; reload and refetch work for the first release.

    Connect the dotsYou already know the server must enforce rules. Now each rule comes from an explicit product decision.

    02 / Scope before complexity

    Choose the first useful slice

    A project becomes manageable when you can name the smallest feature that reaches every layer.

    Build vertically

    First make one authenticated editor create and list a private project issue. Touch the form, request, API, permission check, SQL and UI update together. Finish that path before building every screen or every endpoint.

    Decision. An end-to-end working slice exposes boundary mistakes earlier than completing the whole frontend first.

    Separate release stages

    StageDeliverLeave for later
    First sliceLogin, project access, create/list issuesInvitations, uploads, live updates
    CollaborationOwner-managed membership, comments, statusesAutomation and notifications
    AttachmentsAuthorized uploads and downloadsImage processing
    ReleaseTests, monitoring, backup/restore, deploymentScaling beyond measured needs

    Write acceptance criteria

    Given an editor in project 7, when a valid title is submitted, the API returns 201 with the persisted issue. Given a viewer, the same request returns 403 and creates no row. A non-member receives 404 so the response does not reveal a private project.

    These statements become integration tests and keep implementation choices grounded.

    Connect the dotsKeep a short “later” list. Deferring a feature is a scope decision, rather than a reason to build hidden infrastructure for it now.

    03 / Choose the shape

    Give each layer a responsibility

    Use the separate React + Express arrangement first so the network boundary stays visible. A later chapter maps the same feature to Next.js.

    Choose tools for the job

    PartChoice for this storyResponsibility
    UIReact + TypeScript, developed with ViteForms, views, loading and error states
    APIExpress 5 + TypeScriptHTTP boundaries and permission enforcement
    DatabasePostgreSQL with the pg driverConstraints, queries and transactions
    ValidationZodValidate untrusted request bodies
    LoginA maintained auth flow with server-side sessionsEstablish identity; keep sessions in a production store

    Keep the first architecture small

    One API and one database are enough. Use direct parameterized SQL here so the queries remain visible; an ORM is an alternative, not a prerequisite. Avoid a queue, Redis and WebSockets until a feature or measurement calls for them.

    Decision. A modular monolith is an appropriate starting point for this product.

    Separate identity from project permission

    The login system establishes a user ID. Our project-membership table answers whether that user belongs to a project and what they may do there. A successful login does not grant access to every project.

    All code below is a connected design excerpt, rather than a complete downloadable application. Imports and infrastructure modules such as sessionMiddleware, pool, HttpError and the auth flow must be configured in the real repository.

    05 / Draw the relationships

    Model the rules in the data

    Start with the records and relationships required by the first slice. Add constraints for rules the database can enforce.

    A project is the permission boundary

    A user can join several projects. A project has many membership records and issues. Each membership assigns a role within that project. Each issue belongs to exactly one project.

    Decision. Every issue lookup includes its project ID. Never rely on a project filter that exists only in the UI.

    Write the first migration

    CREATE TABLE users (
  id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  auth_subject text NOT NULL UNIQUE
);
CREATE TABLE projects (
  id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name text NOT NULL CHECK (length(trim(name)) BETWEEN 1 AND 120)
);
CREATE TABLE project_members (
  project_id integer NOT NULL REFERENCES projects(id),
  user_id integer NOT NULL REFERENCES users(id),
  role text NOT NULL CHECK (role IN ('owner', 'editor', 'viewer')),
  active boolean NOT NULL DEFAULT true,
  PRIMARY KEY (project_id, user_id)
);
CREATE TABLE issues (
  id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  project_id integer NOT NULL REFERENCES projects(id),
  created_by integer NOT NULL REFERENCES users(id),
  title text NOT NULL CHECK (length(trim(title)) BETWEEN 1 AND 160),
  description text NOT NULL DEFAULT '' CHECK (length(description) <= 5000),
  status text NOT NULL DEFAULT 'open'
    CHECK (status IN ('open', 'in_progress', 'done')),
  version integer NOT NULL DEFAULT 1,
  created_at timestamptz NOT NULL DEFAULT now(),
  UNIQUE (id, project_id)
);
CREATE INDEX issues_project_created_idx
  ON issues(project_id, created_at DESC, id DESC);

    The auth subject links a local user to the configured identity system. Membership is explicit so an editor in one project can be a viewer in another. Create a project and its initial owner membership in one transaction. Membership management must preserve at least one active owner.

    Choose what survives

    Deactivating membership stops access while preserving issue authorship. Database references and deletion behavior should match retention requirements. Add a comment table with an author and issue reference when comments enter scope; avoid embedding an endlessly growing discussion in one issue row.

    Design list reads early

    Order project issues by created_at DESC, id DESC, with a capped page size. A cursor must carry both sort values and the next query must use the same ordering. The composite index supports this access pattern; verify performance with EXPLAIN when needed.

    Connect the dotsSee Databases for keys, transactions and indexes. A schema is a record of product decisions, not just a place to put JSON.

    06 / Define the boundary

    Agree on the request and response

    Write down the contract before connecting the form. Make expected failures as explicit as success.

    Name the operations

    OperationEndpointPermission
    List issuesGET /api/projects/:projectId/issuesAny active member
    Create issuePOST /api/projects/:projectId/issuesOwner or editor
    Update issuePATCH /api/projects/:projectId/issues/:issueIdOwner or editor
    Add commentPOST /api/projects/:projectId/issues/:issueId/commentsOwner or editor
    Manage membershipProject membership endpointsOwner only

    Keep a consistent envelope

    // POST /api/projects/7/issues
{ "title": "Fix the mobile navbar", "description": "Menu overlaps search." }

// 201 Created
{ "data": { "id": 42, "project_id": 7,
  "title": "Fix the mobile navbar", "status": "open", "version": 1 } }

// 400 Bad Request
{ "error": { "code": "VALIDATION", "message": "Check the title.",
  "field": "title" } }

    The actor ID comes from the verified session. The project ID comes from the validated route. The server sets the initial status and version. A request body must not assign itself an owner, role or creator.

    Validate and whitelist input

    // api/src/features/issues/issue.schema.ts
import { z } from "zod";
export const CreateIssue = z.object({
  title: z.string().trim().min(1).max(160),
  description: z.string().trim().max(5000).default(""),
});
export type CreateIssueInput = z.infer<typeof CreateIssue>;
export type CreateIssueArgs = {
  projectId: number; actorId: number; input: CreateIssueInput;
};
export type Issue = {
  id: number; project_id: number; title: string; description: string;
  status: "open" | "in_progress" | "done"; version: number;
};

    Use result.data from a successful parse when building the insert. Zod's ordinary object schema strips unknown keys; never forward the original req.body wholesale. Define a separate schema for updates.

    Connect the dotsThe contract answers “what crosses this boundary?” The service answers “is this action permitted, and what should it do?”

    07 / Identity and authority

    Decide who can do what

    A permission matrix is easier to review than scattered guesses inside button handlers.

    Write the role matrix

    ActionOwnerEditorViewerNon-member
    Read issues and commentsYesYesYesNo
    Create/update issues and commentYesYesNoNo
    Upload attachmentsYesYesNoNo
    Manage membersYesNoNoNo

    Establish identity first

    Use a maintained login flow. In this case study, the configured session middleware exposes a verified local user ID as req.session.userId. Store sessions outside process memory in production, set appropriate cookie attributes, rotate the session at login, and support logout.

    // api/src/middleware/requireAuth.ts — handler excerpt
if (!req.session?.userId) {
  return res.status(401).json({
    error: { code: "UNAUTHENTICATED", message: "Sign in first." },
  });
}
req.user = { id: req.session.userId };
next();

    Add the matching Express/session TypeScript declarations in the real project. The user ID must come from the server-side session, never a trusted-looking header supplied by the browser. Session middleware reference.

    Guard the cookie boundary

    SameSite and HttpOnly have different jobs. For this same-origin browser app, reject state-changing requests from an unexpected Origin and use the auth framework's appropriate CSRF protection. Apply the policy consistently to login, membership and issue mutations. Hiding an edit button improves usability; it does not enforce the permission.

    Check the specific project

    A member of project 7 must not gain access to project 8 by changing a URL. Check active membership against the route's project ID for every protected operation. Read/update/delete queries also scope the issue to that project. Choose error messages that do not reveal private objects.

    Connect the dotsThis is the distinction between authentication and authorization applied to a real feature.

    08 / The first working feature

    Follow one issue through the stack

    Now connect the decisions to the actual files. Keep the request contract open while you read both sides.

    Receive the request

    // issue.routes.ts — router mounted at /api/projects
router.post("/:projectId/issues", requireAuth, async (req, res, next) => {
  try {
    const rawId = req.params.projectId;
    if (typeof rawId !== "string" || !/^\d+$/.test(rawId)) {
      throw new HttpError(400, "BAD_PROJECT_ID");
    }
    const projectId = Number(rawId);
    if (!Number.isSafeInteger(projectId) || projectId < 1 || projectId > 2147483647) {
      throw new HttpError(400, "BAD_PROJECT_ID");
    }
    const result = CreateIssue.safeParse(req.body);
    if (!result.success) {
      const field = result.error.issues[0]?.path[0];
      throw new HttpError(400, "VALIDATION", typeof field === "string" ? field : undefined);
    }
    const issue = await createIssue({
      projectId, actorId: req.user.id, input: result.data,
    });
    return res.status(201).json({ data: issue });
  } catch (error) { next(error); }
});

    Before this router, configure the session, JSON parser, request-size limits and mutation-origin/CSRF policy. After the router, install one error middleware that translates HttpError(status, code, field?) into the agreed JSON envelope and hides unexpected exception details.

    Enforce the rule in a transaction

    // issue.service.ts — pool, HttpError and insertIssue are imported
import type { CreateIssueArgs, Issue } from "./issue.schema.js";
export async function createIssue({ projectId, actorId, input }: CreateIssueArgs): Promise<Issue> {
  const client = await pool.connect();
  try {
    await client.query("BEGIN");
    const { rows: [member] } = await client.query(
      `SELECT role FROM project_members
       WHERE project_id = $1 AND user_id = $2 AND active = true
       FOR SHARE`, [projectId, actorId]);
    if (!member) throw new HttpError(404, "NOT_FOUND");
    if (!["owner", "editor"].includes(member.role)) {
      throw new HttpError(403, "FORBIDDEN");
    }
    const issue = await insertIssue(client, { projectId, actorId, input });
    await client.query("COMMIT");
    return issue;
  } catch (error) {
    await client.query("ROLLBACK");
    throw error;
  } finally { client.release(); }
}

    The membership row is share-locked while the issue is created, so a concurrent membership revocation waits until this operation finishes. The same database client must execute every statement in the transaction. This is an explicit permission-consistency decision; a transaction alone would not solve that race. pg transactions and PostgreSQL row locks.

    Persist the whitelisted fields

    // issue.repository.ts — same client as the service transaction
import type { PoolClient } from "pg";
import type { CreateIssueArgs, Issue } from "./issue.schema.js";
export async function insertIssue(client: PoolClient, { projectId, actorId, input }: CreateIssueArgs): Promise<Issue> {
  const { rows: [issue] } = await client.query<Issue>(
    `INSERT INTO issues (project_id, created_by, title, description)
     VALUES ($1, $2, $3, $4)
     RETURNING id, project_id, title, description, status, version`,
    [projectId, actorId, input.title, input.description]);
  if (!issue) throw new Error("Insert returned no issue");
  return issue;
}

    Parameters keep user text separate from SQL syntax. The database supplies the ID, initial status and version. Return an explicit set of fields, not user/session secrets or an arbitrary database object.

    Return to the user

    // web/src/features/issues/issueApi.ts
export async function createIssue(projectId: number, input: {
  title: string; description: string;
}) {
  const res = await fetch(`/api/projects/${projectId}/issues`, {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    credentials: "same-origin",
    body: JSON.stringify(input),
  });
  const body = await res.json(); // this API's contract is JSON
  if (!res.ok) throw new Error(body.error?.message ?? `HTTP ${res.status}`);
  return body.data; // type and/or validate this response in the real client
}

// IssueForm.tsx — excerpt inside the component
async function onSubmit(event: React.FormEvent) {
  event.preventDefault();
  if (saving) return;
  setSaving(true);
  setError(null);
  try {
    const saved = await createIssue(projectId, { title, description });
    setNotice(`Issue #${saved.id} saved.`);
    setTitle("");
    setDescription("");
    try {
      await refreshIssues();
    } catch {
      setError("Issue saved. The list could not refresh; reload the list.");
    }
  } catch (error) {
    setError(error instanceof Error ? error.message : "Save failed.");
  } finally { setSaving(false); }
}

    The form uses onSubmit, displays error, and disables submission while saving. The example refetches after saving for simplicity. The handler separates “save succeeded, list refresh failed” so a user does not retry an already-created issue; an idempotency key can make retries safer. A later server-state cache can insert the confirmed result or invalidate the list.

    09 / Add the next behavior

    Grow the feature without losing the boundary

    Only after create/list works do we introduce collaboration and files. Each addition gets its own rules and failure cases.

    Comments need the same permission checks

    A comment records issue, project, author, body and creation time. Verify project membership and comment permission, then verify that the issue belongs to that project. Use a composite reference to prevent storing a comment against the wrong project/issue pair.

    -- Both columns point to the same issue/project pair.
FOREIGN KEY (issue_id, project_id)
  REFERENCES issues(id, project_id)

    Two editors can race

    Suppose both editors read version 3. Their status updates must not silently overwrite each other. Require an expected version, increment it on success, and return 409 if the conditional update changed no row. The permission check still runs first.

    UPDATE issues
SET status = $1, version = version + 1
WHERE id = $2 AND project_id = $3 AND version = $4
RETURNING id, status, version;

    Uploads are a multi-step workflow

    • Authorize the editor and issue before issuing a short-lived upload URL for a server-generated storage key.
    • Create pending attachment metadata, scoped to the project and issue.
    • After upload, verify the stored object and enforce the size/content policy before marking it ready; use scanning where appropriate.
    • Authorize downloads and issue short-lived access rather than exposing private permanent public URLs.
    • Clean up abandoned pending uploads and orphaned objects.

    Introduce asynchronous work when needed

    A comment notification can become a queue job. If saving a comment and guaranteeing a notification must be atomic, write an outbox record in the same database transaction and let a worker deliver it. Handle retries and duplicate delivery. Do not add a queue merely because a full-stack diagram includes one.

    Connect the dotsAttachments involve the database and object storage, which do not share a normal SQL transaction. Pending states and cleanup are part of the design.

    10 / Prove the boundaries

    Test the decisions, not just the happy path

    A useful test suite protects the promises we wrote before the first route.

    Make the acceptance criteria executable

    CaseExpected resultDatabase assertion
    Editor, valid title201 with saved issueExactly one row in the requested project
    Empty or overlong title400 validation errorNo new issue
    Signed out401No new issue
    Viewer in project403No new issue
    Member of a different project404No disclosure or write
    Two updates with one expected versionOne succeeds; one gets 409Exactly one version increment

    Keep a real permission integration test

    // Vitest + Supertest; fixture helpers create isolated test data.
test("a viewer cannot create a project issue", async () => {
  const { project, viewerAgent } = await seedProjectWithViewer();
  const before = await issueCount(project.id);
  const response = await viewerAgent
    .post(`/api/projects/${project.id}/issues`)
    .send({ title: "Attempted write" });
  expect(response.status).toBe(403);
  expect(await issueCount(project.id)).toBe(before);
});

    Use a separate test database. The authenticated agent should go through the configured session flow; do not replace the membership enforcement you are testing with a mock. Test fixture helpers and required imports are abbreviated here.

    Debug one boundary at a time

    For a failed save, first inspect the actual Network request and response. Follow its request ID into the API logs. Confirm which middleware and service ran, then inspect the parameterized query and constraints. A frontend error toast alone does not identify the failing layer.

    Use breakpoints and a failing test to verify the explanation before editing code. Avoid logging session tokens or private attachment contents.

    Connect the dotsTests are evidence for a specific behavior under specified conditions. Passing tests do not prove that every possible interaction is correct.

    11 / First real release

    Plan the release before calling it done

    Deployment is another boundary: code, configuration, data and operational ownership must fit together.

    Build a short release path

    • CI checks types, lint, unit/integration tests and the production build.
    • Use a staging environment with separate database, session store and object storage configuration.
    • Apply reviewed, compatible database migrations through the documented deployment workflow.
    • Serve the UI and /api behind the intended HTTPS origin; configure cookie and proxy trust settings for that topology.
    • Run a smoke test: login, create an issue, reload it, and confirm a viewer is blocked.

    Define how to recover

    Back up the database and test a restore. Keep a known previous application release and understand whether it is compatible with the new schema. A code rollback does not automatically undo a migration. Monitor request failures and latency, and have a way to locate an issue by request ID.

    Use a release checklist

    • Secrets are runtime configuration and excluded from Git, client bundles and images.
    • Production sessions survive API restarts; no default in-memory session store.
    • Upload limits, authorization and cleanup paths are verified.
    • Health/readiness checks and graceful shutdown match the host.
    • A fresh environment can be recreated from documentation, migrations and versioned code.

    Connect the dotsA working localhost screen is one milestone. A recoverable deployment with the correct permissions is the release milestone.

    12 / Learn what stays the same

    Revisit the design with evidence

    Once the feature works, change architecture only for an observed need. Then translate the same responsibilities into Next.js.

    Map the feature to Next.js

    Express versionPossible Next.js App Router version
    React page fetches a project listServer Component reads authorized project data
    POST route and handlerServer Action for the form, or a Route Handler for an HTTP API
    Session and membership checksChecks in actions/routes and the data-access layer
    Service and repositoryThe same server-side responsibilities
    Client state for saving/errorClient interactivity or form-state hooks as appropriate

    Move plumbing, retain the rules

    Next.js does not make a private project secure by itself. Reuse the validated input contract, server-side membership checks, scoped SQL and tests. A Server Action is a callable server boundary; its inputs remain untrusted. Proxy can help with redirects but does not replace data-level authorization.

    Decision. Compare the same feature in two architectures. That makes the framework's contribution visible.

    Let measurements choose the next tool

    Add live updates when users need timely collaboration, then decide between polling, SSE and WebSockets. Add an index after inspecting query plans. Add caching with an invalidation policy when repeated reads justify it. Split a service only when independent deployment or scaling has a concrete benefit.

    Connect the dotsThe aim is to explain each decision well enough that a change of framework does not erase your understanding of the product.

    Wrap up / Think before adding code

    The complete project story

    You now have a repeatable way to turn an idea into a sequence of decisions and verifiable behavior.

    Keep this decision order

    StepQuestion to answer
    ProblemWhose workflow is broken, and what outcome matters?
    ScopeWhat is the smallest useful end-to-end behavior?
    RulesWho may do what, and what must always remain true?
    DataWhich records, relationships and constraints represent those rules?
    BoundariesWhat crosses UI, API, auth and database boundaries?
    ImplementationWhich files own each responsibility?
    EvidenceWhich tests and observations prove the behavior?
    ReleaseHow is it configured, deployed, monitored and recovered?

    Explain the decisions in your own project

    Use AI with a specific decision

    Ask for a comparison when a tradeoff is unclear, a trace through specific files when reading code, or an adversarial review of a permission boundary. Supply the contract and acceptance criteria. Verify the answer against the running request, schema and tests before accepting the change.

    A useful prompt is: “Trace this create-issue request through these files. Identify where project membership is enforced, what can fail, and which integration test proves a viewer cannot write.”
