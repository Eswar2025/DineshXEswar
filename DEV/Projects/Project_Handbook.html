    Week 1 · Monday

    The phone call understand the problem before any code

    Every project starts with a person who has a problem. My first job is to understand it well enough to explain it back. No editor is open yet.

    Monday, 10:30 AM

    The WhatsApp chaos

    Meera, club secretary“We have four badminton courts and about 120 members. People book by messaging the club WhatsApp group. Twice last month two families turned up for the same court at 7 AM. Can you make us a website?”

    I didn't say yes or no yet. “Make a website” isn't a requirement. The real problem is in that message: bookings collide, and nobody can see what is free. If the site solves that, it is a success, even if it looks plain.

    Senior habit

    Write the problem in one sentence, in the client's words, before thinking about technology. Mine was: “Members need to see free courts and book one without colliding with someone else.”

    Monday, 10:45 AM

    The questions I asked

    Most bugs I have shipped came from a question I didn't ask. So I asked these on the call and wrote down the answers:

    • How long is a booking? Always one hour, starting on the hour.
    • Opening hours? 6 AM to 10 PM, every day. So 16 slots per court per day.
    • How far ahead can people book? Up to 7 days. New days open at 7 PM each evening.
    • Limits? At most 2 upcoming bookings per member, so nobody hoards Saturday mornings.
    • Who manages things? Meera and one other person can block courts for maintenance and cancel any booking.
    • Payments? Members pay a monthly fee at the desk. No online payment.

    That last answer saved weeks. Online payment would have meant a payment gateway, refunds, and failed-payment states. Asking was free.

    Monday, 2:00 PM

    A one-page brief

    I turned the notes into one page with three lists and sent it to Meera to confirm. Getting “yes, that's right” in writing prevents arguments later.

    Must have (version 1)LaterNot doing
    Sign up and log inWaitlist for full slotsOnline payments
    See a day's grid: 4 courts × 16 hoursEmail remindersMobile app
    Book a free slot, cancel my ownUsage reports for the committeeChat between members
    Admin: block a court, cancel any booking

    The “Not doing” list matters as much as the first. It is what I point to when a new idea shows up in week 3.

    Monday, 3:00 PM

    Success I can test

    “It works” is not a test. I wrote these sentences so I can check each one later:

    • Two people trying to book the same court and hour: exactly one gets it, the other sees a clear message.
    • A member can't cancel someone else's booking, even by editing the request by hand.
    • A member with 2 upcoming bookings can't make a third.
    • Times show in Indian time for everyone, wherever the server runs.

    The first and fourth lines turned into the two hardest bugs of the project. I didn't know that yet.

    Paper before code screens, flows and the first slice

    Drawing is cheaper than coding. A sketch shows missing screens and missing data before they cost anything.

    Tuesday, 9:30 AM

    Five screens on paper

    I drew boxes on paper, not in a design tool. Five screens covered the whole brief:

    1. Log in / sign up
    2. Day grid: date picker on top, courts as columns, hours as rows, free slots clickable.
    3. Confirm booking: a small dialog, “Court 2, Sat 7 AM. Book?”

    5. Admin: the same grid, plus “block” and “cancel anyone” actions.

    While drawing the grid I noticed the screen needs to show who booked a slot only to admins. Members just see “taken”. That one note became a rule in the API later.

    Tuesday, 11:00 AM

    Walk the main flow

    Then I walked one member through the screens and wrote what happens at each arrow:

    open site ─► not logged in? ─► login ─► day grid (today)
day grid ─► click free slot ─► confirm ─► POST booking
   ├─ success ─► grid refreshes, slot shows "yours"
   ├─ slot taken ─► message, grid refreshes
   └─ limit reached ─► message, link to My bookings

    Every arrow that can fail needs a message on screen. Writing the failures now means the frontend gets error states from day one, not as an afterthought.

    Tuesday, 2:00 PM

    The walking skeleton

    I don't build the whole frontend, then the whole backend. I build one thin path through every layer first, called a walking skeleton:

    Log in → see today's grid → book one slot → see it as “yours”.

    It touches the database, the API, login, the UI and the connection between them. If any layer has a wrong assumption, I find out in week 1, not week 4.

    Tradeoff

    The skeleton looks ugly for days. That's fine. A pretty screen with no working backend hides problems; an ugly screen that really books a court exposes them.

    Tuesday, 4:00 PM

    Why the database comes first

    My build order is data → API contract → API → login → UI → connect them → deploy. The reason is dependency: the UI shows what the API returns, and the API returns what the database stores. If I start with screens, I invent data shapes that the database later can't support.

    It isn't a strict waterfall. Each step takes hours, not weeks, and I loop back when something doesn't fit. The order just means I'm usually building on something that already exists.

    Week 1 · Wednesday to Thursday

    Data first the schema is a record of the rules

    The tables decide what the app can remember and what it can refuse. My first schema was wrong, and that's normal.

    Wednesday, 2:00 PM

    Nouns become tables

    I underlined the nouns in the brief: member, court, booking. Then the relationships:

    • A member has many bookings. A court has many bookings.
    • A booking belongs to exactly one member and one court, at one start time.
    • A member is either a normal member or an admin.

    “Booking” is the table that joins the other two. Most real apps have one table like this, and it's where the hard rules live.

    From the handbooksPrimary and foreign keysNormalization

    Wednesday, 3:30 PM

    My first schema was wrong

    Version one had a Slot table with one row per court per hour per day, pre-filled for weeks ahead, and bookings stored a date string plus an hour number.

    Mistake

    Pre-filled slots meant a daily job to create tomorrow's rows, and a broken job meant no bookable slots. Date strings plus hours made comparing times and handling time zones painful.

    The fix was simpler: don't store free slots at all. Store only bookings, each with a real timestamp. A slot is free when no confirmed booking exists for it. The API computes the grid from opening hours, which never change per row.

    Senior habit

    Store facts that happened (a booking was made), not things you can calculate (which slots are free).

    Thursday, 10:00 AM

    The Prisma schema

    // api/prisma/schema.prisma (Prisma 6 style; match your installed major version)
enum Role { MEMBER ADMIN }
enum BookingStatus { CONFIRMED CANCELLED }

model User {
  id           Int       @id @default(autoincrement())
  email        String    @unique
  name         String
  passwordHash String
  role         Role      @default(MEMBER)
  createdAt    DateTime  @default(now()) @db.Timestamptz(3)
  bookings     Booking[]
}

model Court {
  id       Int       @id @default(autoincrement())
  name     String    @unique
  active   Boolean   @default(true)
  bookings Booking[]
}

model Booking {
  id          Int           @id @default(autoincrement())
  court       Court         @relation(fields: [courtId], references: [id])
  courtId     Int
  user        User          @relation(fields: [userId], references: [id])
  userId      Int
  startsAt    DateTime      @db.Timestamptz(3)  // stored in UTC, always on the hour
  status      BookingStatus @default(CONFIRMED)
  createdAt   DateTime      @default(now()) @db.Timestamptz(3)
  cancelledAt DateTime?     @db.Timestamptz(3)

  @@index([courtId, startsAt])
  @@index([userId, startsAt])
}

    Three decisions are hiding in there:

    • Cancelled bookings stay with a status, not deleted, so admins can see history when there's a dispute.
    • @db.Timestamptz: Prisma's default DateTime column in Postgres has no time zone. I want the database to know these are exact instants.
    • Indexes match the two questions the app asks most: “bookings for this court around this time” and “bookings of this user”.

    Week 2 · Monday to Tuesday

    Building the API, no UI yet route, validate, decide, store

    I built and tested the API with plain HTTP requests before writing any React. If a booking works from the terminal, any later bug is in the UI or the connection, which halves the search.

    Monday, 9:30 AM

    Three small layers

    • routes.ts speaks HTTP: reads the request, validates it, calls the service, sends the response.
    • service.ts holds the rules: opening hours, the 2-booking limit, who may cancel.
    • Prisma talks to the database.

    Routes never contain rules, and services never touch req or res. That way I can test the rules without HTTP, and change HTTP details without touching the rules.

    Zod checks the shape: is it a number, is it a date string. The meaning (on the hour? within opening hours?) is checked in the service, because it needs the club's time zone and today's date. Shape in the route, meaning in the service.

    Monday, 3:00 PM

    The booking route and service (first version)

    // api/src/bookings/routes.ts (Express 5 passes async errors to the error handler)
router.post("/", requireAuth, async (req, res) => {
  const input = CreateBooking.parse(req.body);      // throws ZodError -> 400
  const booking = await createBooking(req.user.id, input);
  res.status(201).json({ data: booking });
});

// api/src/bookings/service.ts (first version, with a hidden race; see chapter 11)
export async function createBooking(userId: number, input: CreateBookingInput) {
  const startsAt = new Date(input.startsAt);
  assertBookableTime(startsAt);                     // on the hour, open, future, within 7 days

  const upcoming = await prisma.booking.count({
    where: { userId, status: "CONFIRMED", startsAt: { gt: new Date() } },
  });
  if (upcoming >= 2) throw new HttpError(422, "BOOKING_LIMIT", "You already have 2 upcoming bookings.");

  const existing = await prisma.booking.findFirst({
    where: { courtId: input.courtId, startsAt, status: "CONFIRMED" },
  });
  if (existing) throw new HttpError(409, "SLOT_TAKEN", "That slot is already booked.");

  return prisma.booking.create({ data: { userId, courtId: input.courtId, startsAt } });
}

    Notice there's no try/catch in the route. In Express 5, a rejected promise from an async handler goes to the error middleware automatically. In Express 4 you had to call next(error) yourself.

    Monday, 4:30 PM

    One error handler

    // api/src/app.ts (after all routers)
app.use((err, req, res, next) => {
  if (err instanceof ZodError) {
    return res.status(400).json({ error: { code: "VALIDATION",
      message: "Check the highlighted fields.", fields: err.flatten().fieldErrors } });
  }
  if (err instanceof HttpError) {
    return res.status(err.status).json({ error: { code: err.code, message: err.message } });
  }
  req.log.error(err);                                 // full details stay in the logs
  res.status(500).json({ error: { code: "INTERNAL", message: "Something went wrong." } });
});

    Expected failures get their real message. Unexpected ones get a generic message, and the stack trace goes to the logs, never to the browser.

    Week 2 · Wednesday to Thursday

    Login and who may do what authentication, then authorization

    Login answers “who are you?”. Permissions answer “may you do this, to this exact thing?”. The second question is where most real security bugs live.

    Wednesday, 10:00 AM

    Sessions stored in Postgres

    // api/src/app.ts
import session from "express-session";
import connectPgSimple from "connect-pg-simple";
const PgStore = connectPgSimple(session);

app.use(express.json({ limit: "20kb" }));
app.use(session({
  store: new PgStore({ pool: sessionPool, createTableIfMissing: true }),
  secret: config.SESSION_SECRET,
  resave: false,
  saveUninitialized: false,
  cookie: {
    httpOnly: true,                 // JavaScript in the page can't read it
    sameSite: "lax",                // not sent on cross-site form posts
    secure: config.isProduction,    // HTTPS only in production
    maxAge: 14 * 24 * 60 * 60 * 1000,
  },
}));

    The default session store keeps sessions in server memory: every restart logs everyone out, and it leaks memory. Storing them in Postgres needed no new service, because the database already exists.

    Wednesday, 2:00 PM

    Signup and login

    router.post("/login", async (req, res, next) => {
  const { email, password } = Login.parse(req.body);
  const user = await prisma.user.findUnique({ where: { email: email.toLowerCase() } });
  const ok = user && await bcrypt.compare(password, user.passwordHash);
  if (!ok) throw new HttpError(401, "BAD_LOGIN", "Email or password is wrong.");

  req.session.regenerate(err => {      // new session id after login
    if (err) return next(err);
    req.session.userId = user.id;
    res.json({ data: { id: user.id, name: user.name, role: user.role } });
  });
});
    • Passwords are stored only as bcrypt hashes. Signup hashes, login compares.
    • The message doesn't say whether the email exists, so nobody can probe for members.
    • regenerate issues a fresh session id at login, which blocks an old, stolen id from becoming a logged-in one.

    From the handbooksPassword hashingAuth libraries

    Wednesday, 4:00 PM

    Guards: requireAuth, requireAdmin

    export async function requireAuth(req, res, next) {
  const id = req.session.userId;
  if (!id) throw new HttpError(401, "UNAUTHENTICATED", "Please log in.");
  const user = await prisma.user.findUnique({ where: { id } });
  if (!user) throw new HttpError(401, "UNAUTHENTICATED", "Please log in.");
  req.user = { id: user.id, role: user.role };
  next();
}

export function requireAdmin(req, res, next) {
  if (req.user.role !== "ADMIN") throw new HttpError(403, "FORBIDDEN", "Admins only.");
  next();
}

    The role is read from the database on each request, not trusted from the browser. If Meera removes someone's admin role, it takes effect on their next click.

    From the handbooksAuth middlewareRoles

    Thursday, 11:00 AM

    The cancel bug a friend found

    I asked Kiran, a club member who codes a little, to try to break the app. Ten minutes later Kiran messaged: “I just cancelled Meera's booking. I changed the number in the URL.”

    Bug

    Cancel checked that you were logged in, but not that the booking was yours: update({ where: { id } }). Any member could cancel any booking by guessing ids.

    // fixed: the owner check is part of the query itself
const where = req.user.role === "ADMIN"
  ? { id, status: "CONFIRMED" }
  : { id, userId: req.user.id, status: "CONFIRMED" };
const { count } = await prisma.booking.updateMany({
  where, data: { status: "CANCELLED", cancelledAt: new Date() },
});
if (count === 0) throw new HttpError(404, "NOT_FOUND", "No active booking with that id.");

    This bug has a name, IDOR (insecure direct object reference), and it's among the most common real-world security bugs. Hiding the Cancel button on other people's bookings did nothing, because Kiran never used the button.

    Senior habit

    For every endpoint that takes an id, ask: “what if I send someone else's id?” Then write a test for it.

    Thursday, 3:00 PM

    One more lock: checking Origin

    Cookies are sent automatically, so another website could try to make a member's browser post to our API (CSRF). sameSite: "lax" already stops the cookie on cross-site posts. I added a second, cheap layer: reject state-changing requests whose Origin header is some other site.

    export function sameOriginOnly(req, res, next) {
  if (["GET", "HEAD", "OPTIONS"].includes(req.method)) return next();
  const origin = req.get("origin");
  if (origin && origin !== config.APP_ORIGIN) {
    throw new HttpError(403, "BAD_ORIGIN", "Request blocked.");
  }
  next();
}

    One fetch wrapper

    // web/src/api.ts
export class ApiError extends Error {
  constructor(public status: number, public code: string, message: string) { super(message); }
}

export async function api<T>(path: string, options: RequestInit = {}): Promise<T> {
  const res = await fetch(`/api${path}`, {
    ...options,
    headers: { "Content-Type": "application/json", ...options.headers },
  });
  const isJson = res.headers.get("content-type")?.includes("application/json");
  const body = isJson ? await res.json() : null;   // a crashed proxy returns HTML
  if (!res.ok) {
    throw new ApiError(res.status, body?.error?.code ?? `HTTP_${res.status}`,
      body?.error?.message ?? "Something went wrong. Please try again.");
  }
  return body?.data as T;
}

    Every request goes through this one function. When something about requests changes (a header, error handling, a redirect to login on 401), I change one file.

    Monday, 3:00 PM

    Four states for every screen

    Each screen that loads data has four states, and I design all of them, not only the happy one:

    • Loading: a gray skeleton grid, so the page doesn't jump.
    • Error: the message plus a “Try again” button.
    • Empty: “No upcoming bookings. Book a court.”, with a link.
    • Ready: the real content.

    Beginners usually build only “ready”. Real users on slow phone data see “loading” and “error” every day.

    Tuesday, 11:00 AM

    The Book button

    async function book(courtId: number, startsAt: string) {
  setPending(`${courtId}|${startsAt}`);              // disables that button
  try {
    await api("/bookings", { method: "POST", body: JSON.stringify({ courtId, startsAt }) });
    toast("Booked. See you on court.");
  } catch (e) {
    if (e instanceof ApiError && e.code === "SLOT_TAKEN") toast("Someone just took that slot.");
    else if (e instanceof ApiError && e.code === "BOOKING_LIMIT") toast(e.message);
    else toast("Booking failed. Check your connection and try again.");
  } finally {
    setPending(null);
    setVersion(v => v + 1);                          // always refetch the grid
  }
}

    The grid refetches whether booking worked or not, because in both cases what's on screen may be out of date. Showing the server's truth is simpler than guessing.

    Week 3 · Wednesday

    Connecting both halves where most beginners get stuck

    The API worked from the terminal. The UI rendered with fake data. Joining them took a day, and almost none of that day was spent on my own code.

    Wednesday, 9:30 AM

    The CORS wall

    Vite served the UI on localhost:5173, Express ran on localhost:3000. My first fetch("http://localhost:3000/api/auth/me") printed a red CORS error in the console.

    Different port means different origin. The browser blocks the page from reading a response from another origin unless that server says it's allowed. My code was fine; the browser was protecting users.

    Two fixes

    (1) Enable CORS on Express with credentials: true and a specific origin, and send credentials: "include" from fetch. (2) Make the browser see only one origin. I chose (2), because production would also be one origin, so development should match.

    From the handbooksCORSURLs and origins

    Wednesday, 10:30 AM

    One origin with the Vite proxy

    // web/vite.config.ts
export default defineConfig({
  plugins: [react()],
  server: {
    port: 5173,
    proxy: { "/api": "http://localhost:3000" },
  },
});

    Now the page calls /api/... on its own origin, and Vite forwards it to Express. No CORS, and the session cookie flows as a normal same-origin cookie. In production, Express serves the built UI files itself, so it's one origin there too.

    Wednesday, 2:00 PM

    The first real booking

    I logged in, clicked Court 2 at 7 AM, and... the grid showed nothing new. No error either.

    I didn't guess. I went boundary by boundary:

    1. Network tab: the POST returned 201 with the booking. So the API and database were fine.
    2. The following GET for the grid returned the booking as taken. So the server knew.
    3. So the bug was in the UI. The grid compared startsAt strings: the API sent ...01:30:00.000Z, the UI built ...01:30:00Z. Same instant, different text.

    Fix: compare times as numbers (new Date(a).getTime()), never as strings. Fifteen minutes, because the Network tab told me which side to look at.

    Senior habit

    When the frontend and backend disagree, open the Network tab first. It shows exactly what crossed the boundary, so you know which half to debug.

    Wednesday, 4:00 PM

    Staying logged in on refresh

    Refreshing the page showed the login screen for a split second, then the grid. App rendered “logged out” before /auth/me answered.

    The fix was a third state. The user is undefined (still checking), null (logged out) or an object (logged in). The app shows a blank shell while it's undefined. Small, but it's the kind of thing users notice immediately.

    Thursday, 3:00 PM

    Login worked, then didn't

    On staging, login returned 200, then every next request returned 401. In the Network tab, the login response had no Set-Cookie header at all.

    Bug

    In production the cookie is secure: true, sent only over HTTPS. The host's proxy handles HTTPS and forwards plain HTTP to Express. Express saw HTTP, decided the connection wasn't secure, and silently didn't set the cookie.

    // tell Express it sits behind one trusted proxy
if (config.NODE_ENV === "production") app.set("trust proxy", 1);

    With this, Express reads the proxy's X-Forwarded-Proto header and knows the original request was HTTPS. One line, but it took an hour to find, because nothing printed an error.

    From the handbooksReverse proxiesHTTPS

    Friday, 10:00 AM

    Every slot was 5½ hours off

    Meera tried staging and messaged: “Why does the first slot say 11:30 AM?” On my laptop it said 6:00 AM.

    // the buggy helper
const d = new Date("2026-12-05");   // midnight UTC
d.setHours(6 + i);                   // 6 o'clock in the SERVER's time zone

    My laptop is set to India time, so setHours(6) meant 6 AM India. The server runs in UTC, so it meant 6 AM UTC, which is 11:30 AM in India. Same code, different machine, different answer.

    // fixed: always compute slots in the club's time zone, explicitly
import { DateTime } from "luxon";
const CLUB_ZONE = "Asia/Kolkata";

export function slotsForDay(dateISO: string): Date[] {
  const day = DateTime.fromISO(dateISO, { zone: CLUB_ZONE }).startOf("day");
  return Array.from({ length: 16 }, (_, i) => day.set({ hour: 6 + i }).toUTC().toJSDate());
}
    Rule I follow now

    Store and send instants in UTC. Convert to a human time zone only at the edges: when computing “6 AM at the club” and when displaying. Never rely on the machine's own time zone.

    I also added a test that runs with TZ=UTC set, so this bug can't come back silently.

    Friday, 7 PM the race condition

    Meera invited 30 members to try the app. New days open at 7 PM. At 7:00:01, thirty people clicked Saturday morning at the same time.

    Friday, 7:04 PM

    Two bookings, one court

    TimeRequest A (Ravi)Request B (Sana)

    From the handbooksTransactionsThe event loop

    Friday, 9:00 PM

    Let the database decide

    Code can't reliably enforce “only one” across parallel requests. The database can, with a unique index. Cancelled bookings must not block a slot, so it's a partial unique index: unique only among confirmed bookings.

    npx prisma migrate dev --create-only --name one_booking_per_slot
    -- prisma/migrations/..._one_booking_per_slot/migration.sql (edited by hand)
CREATE UNIQUE INDEX "booking_one_confirmed_per_slot"
  ON "Booking" ("courtId", "startsAt")
  WHERE status = 'CONFIRMED';

    Our Prisma schema couldn't describe a partial index, so I wrote this migration by hand. Check whether your Prisma version supports it in the schema.

    Watch out

    Prisma compares the database with schema.prisma, so an index it can't see may show up as a DROP INDEX in a later generated migration. I now read every generated migration before applying it.

    From the handbooksIndexesMigrations

    Friday, 10:00 PM

    Turning the error into a 409

    // api/src/bookings/service.ts (second version)
import { Prisma } from "@prisma/client";

try {
  return await prisma.booking.create({ data: { userId, courtId, startsAt } });
} catch (err) {
  if (err instanceof Prisma.PrismaClientKnownRequestError && err.code === "P2002") {
    const mine = await prisma.booking.findFirst({
      where: { userId, courtId, startsAt, status: "CONFIRMED" },
    });
    if (mine) return mine;                         // the same member clicked twice
    throw new HttpError(409, "SLOT_TAKEN", "Someone booked this slot a moment ago.");
  }
  throw err;
}

    I kept the friendly findFirst check before the insert, because it gives a fast answer in the common case. But the index is the real guard, and the catch handles the rare case where two requests pass the check together.

    I didn't trust my memory of the error code. I forced a conflict in a test and logged err.code to confirm it was P2002 before writing this.

    Friday, 10:30 PM

    The double click

    One member got “Someone just took that slot”, and the slot was theirs. They had double-clicked. The first click booked it, and the second hit the unique index.

    Two fixes, one on each side:

    • UI: the button is disabled while its request is pending (already done in chapter 8, but this member was on an old cached version).
    • API: if the conflict is with the same member's own booking, return that booking instead of an error, as in the code above. Repeating the same request now gives the same result.

    That property is called idempotency. For payments, teams use an explicit idempotency key per request. For a booking, “same member, court and time” was a natural key already.

    From the handbooksIdempotency

    Saturday, 11:00 AM

    The limit has the same race, and I kept it

    The “max 2 upcoming bookings” check has the same problem: two parallel requests could both count 1 and both insert, giving 3. I could fix it with a row lock on the user or a serializable transaction.

    Tradeoff

    The worst case is one member with 3 bookings, rarely, and an admin can cancel one. The fix adds locking complexity to every booking. I wrote the risk in the README and left it. A double-booked court is a real problem; a third booking isn't.

    Seniors don't fix every theoretical issue. They decide which ones matter and write down the ones they accept.

    Week 5 · Tuesday

    The slow email when to move work out of the request

    Meera asked for a confirmation email after each booking. The first version took twenty minutes to write and caused a problem on its first busy evening.

    Tuesday, 10:00 AM

    Sending inside the request

    const booking = await createBooking(req.user.id, input);
await sendConfirmationEmail(booking);   // calls the email provider's API
res.status(201).json({ data: booking });

    On Friday evening the email provider was slow: about 4 seconds per call. Every booking took 4 seconds, so people clicked again. Once the provider timed out and the member got a 500 error, even though the booking was already saved.

    Bug

    A side effect (email) decided whether the main action (booking) looked successful. The booking succeeded; the response said it failed.

    Tuesday, 11:00 AM

    Why not just skip await?

    The tempting fix is to call sendConfirmationEmail(booking) without await. The response returns fast. But if the server restarts during a deploy, or the provider is down for 10 minutes, those emails are lost forever and nobody knows.

    I needed the email to be recorded as owed in the same moment as the booking, then sent separately, with retries.

    From the handbooksQueuesSending email

    Tuesday, 2:00 PM

    An outbox table and a worker

    // in the booking service: both rows commit together, or neither does
const booking = await prisma.$transaction(async tx => {
  const b = await tx.booking.create({ data: { userId, courtId, startsAt } });
  await tx.outbox.create({ data: { type: "booking.confirmed", payload: { bookingId: b.id } } });
  return b;
});

// api/src/worker.ts (a separate process on the same host)
async function tick() {
  const jobs = await prisma.outbox.findMany({
    where: { sentAt: null, attempts: { lt: 5 } }, orderBy: { createdAt: "asc" }, take: 10,
  });
  for (const job of jobs) {
    try {
      await sendEmailFor(job);
      await prisma.outbox.update({ where: { id: job.id }, data: { sentAt: new Date() } });
    } catch (err) {
      await prisma.outbox.update({ where: { id: job.id }, data: { attempts: { increment: 1 } } });
      log.warn({ jobId: job.id, err }, "email failed, will retry");
    }
  }
}
while (true) { await tick(); await new Promise(r => setTimeout(r, 10_000)); }

    Bookings are fast again, emails survive restarts, and a failed email retries up to 5 times. This pattern is called a transactional outbox.

    What I accepted

    If the email sends but saving sentAt fails, the member gets the email twice. For a booking confirmation that's fine. With one worker, I didn't need row locking; two workers would need FOR UPDATE SKIP LOCKED so they don't take the same job.

    Why not Redis or a queue service?

    The outbox uses the database we already have. A dedicated queue becomes worth it when there are many job types or high volume. Here, there's one job type and a few hundred emails a week.

    Week 6

    Changing a live database safely

    A week after launch, Meera wanted bookings to show a “partner name”. Adding a nullable column is safe. Renaming one isn't: the old code still running during the deploy would crash on the missing name.

    So database changes go in steps, called expand and contract: add the new column, deploy code that writes both, backfill old rows, switch reads, and only later remove the old column. Rolling back the code never needs the database rolled back.

    Senior habit

    A code rollback doesn't undo a migration. Before each release, ask: “if I roll back the code, does it still work with the new database?”
