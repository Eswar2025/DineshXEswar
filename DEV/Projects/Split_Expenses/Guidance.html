    Explain the dinner before the code

    Dinesh pays ₹900 for dinner shared equally by Dinesh, Eswar, and Priya. Each person’s share is ₹300. Dinesh has already paid his own share and ₹600 for the others.

    Balances are Dinesh +₹600, Eswar −₹300, Priya −₹300. Positive means “should receive”; negative means “owes”. Add them together: zero.

    When Eswar repays Dinesh ₹300, record a settlement. Balances become +₹300, ₹0, −₹300. The dinner still cost ₹900; the settlement is a separate record.

    Before you move on

    Explain those numbers in your own words. If you cannot explain the calculation yet, repeat it with ₹600 and draw arrows for the repayments.

    A small, understandable setup

    Choose tools and learn as needed

    Pick a stack you want to practice and keep the first setup small.

    Make a few explicit decisions

    You can choose any frontend, server, database, and libraries. React, Node/Express, and PostgreSQL are one possible combination that fits this repo’s learning direction. A full-stack framework or a different database can satisfy the same requirements.

    Write down your choices in the workbook’s notes with one reason each. Decide whether you and Dinesh are building one shared app or comparing separate implementations before creating competing structures.

    Get a minimal page running, then a server response, then a database connection. Write down the exact commands that work for your setup. Keep configuration secrets out of Git.

    Concrete actions for today

    Complete your first session

    Aim for a clear plan and one visible screen. Save the full backend flow for the next milestones.

    Follow this sequence

    1. Open the workbook and choose Eswar. Read “Define the first version”. Write one sentence: “A group member can record a shared expense and see everyone’s balance.”
    2. Work out the ₹900 example. Write paid amount, share, and resulting balance for each person. Check the total is zero.
    3. Sketch three views. A group list, a group detail page, and an add-expense form. Paper is enough. Label payer and participants separately.
    4. Write your stack choices. Create the smallest working project inside app/. Add the commands you used to your application’s run instructions.
    5. Render one group with sample data. Show “Weekend trip”, the three names, the dinner expense, and the expected balances. Hard-coded sample records are fine for this milestone.
    6. Try the screen and record your next step. Check it at phone width, explain it to Dinesh, and mark only the workbook checks you actually verified. Note the next unfinished task.

    You can stop at a sensible boundary and continue later. The first session does not need custom splits, authentication, deployment, or a finished app.

    What you should have afterward

    A project sentence, a correct calculation, screen sketches, recorded tool choices, and a sample group page you can run and explain. If setup takes longer, record the exact blocker and keep your sketches and calculations.

    Keep the first real flow narrow

    Your first backend-backed journey is: create one group → add the three members → save one equal-split dinner → read balances. Use local seeded identities while learning; add proper authentication and permissions before public use.

    Finish and verify that journey before adding charts, live notifications, receipts, payment integrations, or extra split modes. A small complete path is a useful base for every later feature.

    Repeat this for each task

    Work through one feature

    Turn “add an expense” into a sequence you can implement and check.

    Trace “save dinner” through the system

    1. Read the requirement. What inputs are required? What should happen on success and on invalid input? Write the expected result before implementation.
    2. Write a sample contract. Your request needs the group, description, amount in paise, payer, date, split mode, and selected participants. The signed-in actor comes from the verified identity once authentication is added.
    3. Build the calculation separately. Allocate the shares and derive balances using ordinary data. Run the ₹900 and ₹100 examples without a browser or database.
    4. Implement the server operation. Check identity/access when available, validate all inputs and group membership, calculate shares, and save the expense plus shares atomically.
    5. Call the backend directly. Use an API client, a small script, or your framework’s test tools. Confirm one valid request and one invalid request before wiring the form.
    6. Connect the form. Show saving state, prevent repeat clicks, keep input on failure, and refresh both history and balances after success.
    7. Prove it works. Refresh the page, inspect stored records, and check the exact balances. Run the task’s failure cases. Then mark the corresponding workbook checks.
    Completion means observable behavior

    “I wrote the handler” is a step. “The expense saves once, survives refresh, and produces +600/−300/−300” is evidence that the feature works.

    Try, then reveal a hint

    Attempt a small version first. If you cannot identify the next step, open Hint 1. Try again before opening Hint 2. Use the deeper hint when you need a more concrete breakdown.

    When you use a snippet or pseudocode, explain each step and try a different input. Record the lesson in the workbook notes so you can teach it to each other.

    Use a short review every time

    • Does the normal case work?
    • What happens with invalid input?
    • What remains after refresh or restart?
    • Can a direct request bypass the UI rules?
    • Can you explain the result and why the code produces it?

    Check off a task after performing its stated check. Keep a failing case unchecked and write down what you observed.

    Debug one thing at a time

    Find the boundary when you get stuck

    Locate where the actual behavior first differs from what you expected.

    Follow the evidence

    SymptomFirst thing to inspect
    The page does not renderBrowser console, development server output, and the smallest broken component.
    Clicking save does nothingDoes the submit handler run? Does a request appear in the network panel?
    The request failsRequest URL, method, payload, response status/body, and server log for that operation.
    Saving succeeds but data disappearsDatabase records, connection configuration, and whether reads use the same database.
    Balances are wrongPaid paise, stored shares, signs, selected participants, and whether an old expense was counted twice.
    One paisa is missingThe remainder allocation and whether stored shares sum exactly to the expense.
    One account sees another groupThe server’s membership check and query scope on that specific request.
    An edit sometimes loses another editWhether the version condition is part of the actual atomic database write.

    Reduce the problem to one group and one record. Compare expected and actual data at each boundary: form → request → handler → calculation → database → response → rendered result.

    Bring a small, specific question

    When asking Dinesh or an assistant, include the current task, expected behavior, actual behavior, relevant code, and one reproducible input. Leave out passwords, tokens, connection strings, and private session data.

    I am implementing the equal-split calculation.
Input: 10,000 paise, three participants in a fixed order.
Expected: 3,334 / 3,333 / 3,333.
Actual: 3,333 / 3,333 / 3,333.
Here is my allocation function and the check that fails.
Give me a hint about the missing step first.

    After resolving it, write the cause and the fix in your notes. Add a repeatable test when the bug affects calculation, access, or persistent data.

    Learn by explaining

    Review together and choose the next step

    End a session knowing what works, what you learned, and what you will do next.

    Use your Google Meet well

    1. Choose one small task and predict its result together.
    2. One person types and explains; the other checks assumptions and asks questions.
    3. Run the normal case and one failure case. Swap roles for the next task.
    4. Explain the request flow or calculation without reading the code line by line.
    5. Record one decision, one remaining doubt, and the next action.

    If you are building separate versions, compare the same inputs and expected behavior. If you share one app, agree on file ownership for the current task and coordinate before editing the same files.

    Leave the project ready to resume

    • Mark the verified workbook checks under your own profile.
    • Save decisions and open questions in the stage notes.
    • Export progress when you need a backup or want to share your notes.
    • Review git status and the changed code before a commit. Pull before starting repo work; coordinate overlapping edits.
    • Write an exact next action, such as “connect the expense form to the route and preserve input on failure”.

    For the final project demo, create a group, add the dinner, edit it, record a repayment, and explain each balance. Use the workbook’s deployment stage for the final setup and hosting checks.

    The habit to keep

    Read one task, predict its behavior, implement a small piece, verify it, and explain it. Then continue to the next unfinished check.
